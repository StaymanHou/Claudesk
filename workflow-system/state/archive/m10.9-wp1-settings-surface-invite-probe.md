## Problem Statement

M10.9 needs a `workflow_features_enabled` toggle and a one-time evangelistic invite, but two prerequisite decisions are unresolved and both are expensive to rework once built. **(a)** There is **no dedicated Settings UI in Claudesk today** — the four existing app-global settings (permission-mode `<select>`, time-tracking checkbox, update-notifications checkbox + check button) live in an ad-hoc `ProjectPicker` strip (`ProjectPicker.tsx:396-445`) that is only reachable when *no workspace is focused* (`appView.ts` → `viewFor` returns `"picker"` only when `focusedId === null`), with the native View menu as the in-workspace escape hatch; `⌘,` is unbound and no `Settings…` menu item exists. Meanwhile `roadmap.md:283` already assigns the **consolidated** Settings surface to M14, so building a real Settings overlay now risks pulling M14's work forward. **(b)** The invite must fire exactly once while OFF and never re-nag after enable-or-dismiss (return contract §4b), which requires deciding its trigger condition, its `AppSettings` persistence shape (including the disable-after-enable case, where a naive `seen` bool would be ambiguous), and a dev-build re-drive override so WP5 can retest the first-run path without hand-wiping `settings.json`.

This is a **probe**: its deliverable is two written verdicts in `wbs.md` → "Probe outcomes", each grounded in the as-built code and — for (a) and the invite's scope — an explicit run of the `[[new-surface-must-earn-its-place-against-existing-ones]]` decision rule. WP2 builds the gate against verdict (a); WP3 builds the invite against verdict (b). No production code ships in this WP (a plan-only WP is a legitimate probe outcome per the WBS's own framing of WP4).

**3rd-party dependency:** none. The companion `my-claude-code-customization` repo is a *documentation* dependency already delivered as static text (`HANDOFF-from-mccc-2026-07-28.md` + the companion repo's `onboarding-flow-spec.md`) — not a runtime API, so no probe-before-plan gate applies (WBS "Dependency map" §4 n/a). WP3.1 reads those files directly.

**Context already established (do not re-derive):**
- Nothing shipped today is workflow-coupled, so OFF=byte-identical is *already* true — there is no de-wiring work (WBS "Baseline finding").
- `[[gate-substrate-dependent-feature-class-behind-default-off-opt-in]]` is settled and taken at Rule 2 (agrees with common sense): default OFF for everyone including the operator, set by *applicability* not audience size; no environment auto-detection; enable is a pure app-state flip touching nothing in `~/.claude/`.
- The established settings state-discipline this feature must clone (read at plan time): seed-from-backend on mount → `listen()` to a broadcast event → optimistic `setState` → `invoke()` set → revert-on-IPC-failure + error toast (`ProjectPicker.tsx:158-330`), with the native menu mirrored via an `apply_*_to_menu` handle-stash (`app_menu/mod.rs:78-131`) and ids duplicated byte-identically Rust `FUNCTIONAL_IDS` ↔ TS `MENU_IDS` (pinned by an existing test).

## Notes on verification tiers for this WP

This is a **decision probe with no production code**, so the tiers land differently than on a build WP — flagged here at plan time so no tier is over- or under-claimed later:

- **verify-auto:** the repo's existing gates must still pass untouched (`pnpm tsc --noEmit`, `pnpm lint`, `cargo test`) — this WP edits only markdown, so a *regression* here means something unintended was touched. Plus the per-phase CLI outcome greps above.
- **verify-self:** agent-drivable **in full** for both phases — every outcome is a `grep`/`git ls-files` check against files in the repo. **No MCP-bridge session and no running app are needed** (nothing is rendered), so per the project's verify-self convention this WP does **not** carry live checks to the operator.
- **verify-human:** the substantive gate — the operator reviews the two *decisions*, since a probe's value is the judgment, not the mechanics. Both verdicts are also **design-prior capture checkpoints** (WBS "Design-prior consult": WP1's Settings-surface call and the invite-copy call): if the operator's reasoning reveals a transferable product-design lean, propose a prior then — read existing priors and dedup/conflict-check first, propose never auto-write.
- **verify-codify:** expected to be a documented **no-op** for both phases (there is no behavior to pin — the tests that make these decisions enforceable are WP2.5's OFF-invariant guard and WP3.3's copy-fidelity test, both explicitly scoped to those WPs). Recording the no-op with its reason is the deliverable.

## Retrospect

- **What changed in our understanding:** **A screenshot beat every file I read.** The probe's central question — where the gate's toggle lives — was answered *wrongly* by reading `ProjectPicker.tsx`, `appView.ts`, and `app_menu/mod.rs` end-to-end, and answered *correctly* the moment the operator pasted a picture of the running picker. The files told me the strip *exists* and is picker-only-reachable; the screenshot told me it **eats ~1/4–1/3 of the modal above the project list**. Those support opposite verdicts. The transferable form: **when a decision's host is an existing screen, code-reading yields structure but not cost, and layout decisions are decided by cost.** Corollary discovered the same way: I framed the question as *"where does one boolean go?"* when the live question was *"has the collection outgrown its container?"* — the framing, not the analysis, was the error, and no amount of rigor inside a wrong frame recovers it.
- **Assumptions that held:** the probe-before-build ordering paid off exactly as the WBS predicted (both decisions were cheap on paper and would have been expensive to rework once a surface existed); the `time_tracking_enabled` flag really is a complete template for the gate's persistence; the established seed→listen→optimistic-set→revert discipline is uniform enough to clone without inventing anything; and `[[new-surface-must-earn-its-place-against-existing-ones]]` was the right prior to run — it produced the correct answer **both times**, first rejecting a panel and then requiring one, because the *inputs* changed rather than the rule.
- **Assumptions that were wrong:**
  1. **That verify-auto/self/codify on a docs-only phase is ceremony.** It caught four real defects: a blank-line citation (`roadmap.md:283`), an `AppSettings` field-count off-by-one at 4 sites (`cc_yolo` omitted — **2 of those sites predated this session**), and via review-quality a **jointly-unrealizable pair of decisions**. The cheap greps found what careful prose-writing had missed.
  2. **That a two-button invite was a complete model.** `[Enable]`/`[Not now]` with `[Not now]` meaning *permanent* is a **mislabeled control**. The operator supplied the missing third intent; the codebase then confirmed it already had the exact precedent (`dismissBanner` vs `skipVersion`, same file). I had read `useUpdater.ts` and still missed that the two-way split was sitting there.
  3. **That "the enum variants are diagnostics, not branching" was a safe simplification.** It was true only of the incomplete model, and I wrote it as a constraint *on WP3*. A confidently-stated instruction derived from an unexamined premise is worse than no instruction.
  4. **That fixing an instance fixes the class.** I found and fixed one comment-vs-code citation slip (`ProjectPicker.tsx:252→253`), noted the lesson — and the reviewer then found the identical slip in `EditorSplit.tsx:458`. I fixed the finding, not the pattern.
- **Approach delta:** planned as two decision phases with the verdicts as the sole deliverable, and that structure held — but the *content* was revised twice at human gates (settings surface (ii)→(iii-b); invite 2→3 buttons), and each revision rippled into 5–6 downstream WBS sites plus a WP re-size (WP2 S→M). Beyond plan: I compiled the proposed Rust in a throwaway crate at verify-auto rather than eyeballing it, then **re-compiled** the corrected 3-arm model at verify-codify rather than leaving a stale proof for WP3 — the second run's decisive assertion (`[Later] != [Dismiss]` in a fresh session) is what turned the operator's correction from *accepted* into *proved*. Also beyond plan: three MAJOR review findings were fixed in place instead of auto-backlogged (autopilot's default), because they were defects in this WP's own deliverable and backlogging them would have shipped WP3 a spec I knew to be unbuildable.
