## Problem Statement

WP3.5a gave Claudesk the ability to *install* the companion workflow system (clone + `install.sh` + provenance record). There is no back-out path: a user who disables `workflow_features_enabled` on a **managed** install is left with the substrate in place, and a user who hand-runs `uninstall.sh` leaves a stale provenance record claiming an install that is gone. WP3.5b builds the uninstall path — **the first deleting code in Claudesk that can touch state outside its own app-data dir** — which is why the refuse-guard is task ONE, in production code, before any deleting path exists.

The failure mode this WP is designed against: deleting the operator's live workflow system (`~/.claude/skills/` symlinks into their actively-edited companion repo). The provenance model (recorded at install time, never inferred from a resolved path) is what prevents it; the refuse-guard is its production-code enforcement; `uninstall.sh`'s own into-repo-only guard is the independent second line. **Both, not either.**

Problem statement unchanged — [2026-07-31, F9b re-entry for P3.verify-self.1]: the finding is a truthfulness bug in how the substrate's state is *read* after the removal this WP performs, not a change to what the WP is for. Two fixes: presence now requires a non-empty skills dir (an empty leftover is not an install), and the uninstall slot renders in both resolved arms so a successful removal doesn't unmount its own confirmation. Both are this WP's own surface.

Problem statement unchanged — [2026-07-31, F12 re-entry for P2.verify-human.2]: the finding is a latent WP3.5a UI bug (install-wizard done step unmounts on the absent→installed arm flip) surfaced by Phase 2's boundary check, not a shift in this WP's problem. Fixed via `armRendersInstallSlot` (pure decision) + `{slot}` rendered in both allowed arms + value tests + a mutation-proven two-render-site count guard.

## User Stories

- As a **secondary user who installed the substrate via Claudesk**, I want disabling the workflow features to offer a real uninstall — with a truthful preview of exactly what will be removed — so that backing out is one wizard, not a hand-run script.
- As a **secondary user who wants the UI off but the substrate kept**, I want a distinct `[Keep mccc]` choice so that disabling the gate doesn't force removal.
- As a **user who opened the dialog by accident**, I want `[Cancel]` to revert the gate to enabled so that cancelling the wizard cancels the toggle — I never land in `[Keep mccc]`'s state without choosing it.
- As the **operator (developer install, permanently)**, I want Claudesk to *name* my provenance state and explain why no install/uninstall button exists for me, and to structurally refuse — in production code, not test code — to ever delete my live repo or symlinks.

## Acceptance Criteria

The feature is done when all of the following hold (task numbers are the WBS's, preserved):

1. **(3.5.2 — task ONE)** A refuse-guard exists **in production code**, landed **before any deleting path** in commit/task order:
   - Every deleting operation (clone-dir removal; any file deletion Claudesk itself performs) consumes **only the recorded, canonicalized managed dir** — never a path inferred from where a symlink resolves, never a caller-supplied path.
   - It hard-refuses when: no well-formed record exists; the recorded path fails canonicalization; the canonicalized target is `$HOME`, `~/.claude`, an ancestor of either, or filesystem root; or the target does not look like the managed clone (e.g. missing `uninstall.sh`).
   - Both sides of every containment/equality comparison are **canonicalized** (the macOS `/var`→`/private/var` trap), and the compared production value is a **production-reported observation**, never a test-constructed literal (the WP3.5a constant-true-assert lesson). `starts_with` on unresolved paths is blind to symlink escapes — proven live in WP3.5a by a planted mutation both containment tests passed. Meta-tests that exercise an escape must **create the escape path on disk** so both sides canonicalize consistently.
   - `Managed` is never inferred from location: a hand-clone sitting in `~/.claudesk/vendor/` with no record stays `Developer` and is refused (WP3.5a codified `a_substrate_sitting_in_the_vendor_dir_is_still_not_managed_without_a_record`; "adopt-on-detect" was explicitly rejected at spec).
   - The **refusals are unit-tested** (each refusal arm individually), and mutation-proven at verify: break the guard, watch a test fail, restore.
2. **(3.5.3b)** Provenance → UI consequences are rendered and the state is **legible** (resolves `SURFACE-2026-07-30-WP3.5A-PROVENANCE-STATE-NOT-LEGIBLE-IN-UI`):
   - **absent** → install affordance only (existing); nothing to uninstall.
   - **managed** → the row names the state ("installed by Claudesk") and how uninstall is reached (disable the toggle).
   - **developer** → the row names the state and says *why* there is no button (e.g. "installed outside Claudesk — Claudesk won't modify or remove it"), keeping WP3's hand-run commands. **Never any uninstall affordance.**
3. **(3.5.5)** The three-intent dialog fires when — and only when — the user disables `workflow_features_enabled` while provenance is `managed`:
   - `[Uninstall]` → runs the removal sequence (AC 5); gate → disabled.
   - `[Keep mccc]` → substrate untouched, record untouched; gate → disabled.
   - `[Cancel]` → substrate untouched, record untouched; **gate reverts to enabled** (the persisted value never lands on disabled).
   - Disabling with provenance `developer` or `absent` shows **no dialog** — the gate just flips.
4. **(3.5.5b)** The preview shown before `[Uninstall]` acts is the **real output of `uninstall.sh --dry-run`** run against the recorded clone — not a Claudesk-composed list — so preview and action share one source of truth. The preview must correctly render output shapes proven to occur in real sandbox runs: `[skip]`/`[ok]` lines, the **dangling into-repo link** case (clone wiped while symlinks survive), and the **unconditional legacy `claude-time` removals** (upstream design rescuing pre-retirement installs — not a bug to explain away).
5. **Removal sequence + record lifecycle** (resolves `SURFACE-2026-07-30-WP3.5B-UNINSTALL-MUST-CLEAR-THE-PROVENANCE-RECORD`): `[Uninstall]` runs, in order: the recorded clone's `./uninstall.sh` → removal of the managed clone directory (guarded per AC 1) → **deletion of `~/.claudesk/install-record.json` LAST**. Mirror of install's write-last: a failed uninstall leaves the record describing what still exists. After full success the substrate row resolves `absent` and the install affordance returns.
6. **(3.5.6b)** Uninstall-half terminal states live in the same pure module as the install half (`terminal.rs` vocabulary extended), unit-tested as a table: script non-zero / clone-dir removal fails / record-delete fails / mid-run cancel — every arm decides record-kept-vs-deleted and the gate outcome explicitly, per-arm (no shared default). A failed or partial uninstall **never** deletes the record. **Table coverage is enforced by a compiler-exhaustive `match` that *produces* the rows** — never a counted/enumerated guard (WP3.5a proved three times that remember-to-register guards are theatre; `SURFACE-2026-07-29-REMEMBER-TO-REGISTER-GUARDS-ARE-NOT-GUARDS`). **Cancel is polled between steps only** — never kill a running `uninstall.sh` (mirror of install's no-kill-mid-clone decision), and the UI says so while the script runs.
7. **(absorbed)** `SURFACE-2026-07-29-QUALITY-WP3.5A-SOURCE-GUARD-CONSOLIDATION` is paid as part of building the refuse-guard: one shared `#[cfg(test)]` source-extractor helper (split on `mod tests`, comment-stripping); one ambient-root guard per module; the three "ships no delete" guards collapsed into one crate-level guard re-scoped to "only the uninstall path may delete, and only via the refuse-guard"; the position tripwire deleted.
8. **(3.5.7b)** Verified against the **sandbox** (fake `$HOME` via `sandbox.rs` + the sandboxed-launch convention for live tiers), **including proving the refuse-guard bites** (a run aimed at a non-recorded path is refused and deletes nothing — asserted via `assert_writes_stay_under`). At least one test asserts the **composed end-to-end path** — real uninstall run → record cleared → `resolve_state` → `Absent` — not hand-built records (closes WP3.5a's known composition gap). The live uninstall against the operator's real `~/.claude/` is **operator-only**, never agent-driven — and for this WP the **live sandboxed-`$HOME` verify-human pass happens BEFORE finalize/close**, not deferred to a post-finalize batch (WP3.5a's deferred batch found 7 findings after finalize; a destructive WP does not absorb that risk).

## Out of Scope

- **Any update path** (fetch/pull/behind-count) — operator decision: option A, install/uninstall only.
- **Per-project memory symlink removal** (`uninstall.sh --project`) — the wizard never passes `--project`; memory links are per-project artifacts the workflow system manages, and the script's default omits them.
- **A standalone `[Uninstall…]` button in the substrate row.** The dialog's gate semantics ([Cancel] → re-enable) only make sense triggered from the toggle; a second entry point would need different semantics. `[PRIOR: new-surface-must-earn-its-place-against-existing-ones]` agrees with the common-sense default here — one trigger, no redundant affordance. The managed row's copy points at the toggle instead.
- **Editing `~/.claude/settings.json`** — the script only prints removable permissions; the wizard surfaces that output, symmetric to install's consent copy.
- **Restoring/removing `CLAUDE.md.bak`** or any cleanup beyond what `uninstall.sh` does; **deleting `~/.claudesk/` itself** (only the clone dir and the record go).
- **Changing `uninstall.sh`'s behavior** — Claudesk shells out to the script, never reimplements it (§4c anti-brittleness).

## Technical Constraints

- **Sandbox discipline is non-negotiable** (`SURFACE-2026-07-28-MCCC-INSTALL-FEATURE-NEEDS-SANDBOXED-DEV-AND-VERIFY`, high): injectable roots everywhere, no ambient `home_dir()`/`env::var("HOME")` below `commands.rs` (source-guarded), all destructive tests against `sandbox.rs`'s fake home. Dev/verify must never touch the real `~/.claude/` or the operator's companion repo.
- **Inherited WP3.5a vocabulary to extend, not fork:** `provenance::read_record` (degraded reads → `None` → `Developer`), `resolve_state`, `runner.rs` pure `(program, args)` builders + `OutputSink`, `terminal.rs` pure reducer (runner reports, terminal decides, caller acts), `RunGuard` (Drop-based panic boundary — mandatory on the uninstall worker), `InstallError`-style per-arm decisions.
- **Script dependency is probed, not assumed:** `uninstall.sh` was audited 2026-07-29 against the real repo and hand-run (incl. `--dry-run`) against the sandbox at WP3.5a verify-human. Known behaviors: into-repo-only symlink removal with dangling-link fallback; `[skip]` for foreign links/real files; marker-block excision with `.bak`; print-only settings.json; idempotent; `--dry-run` accurate. No other 3rd-party dependency.
- **Frontend toggle interception:** the gate control's optimistic-set/persist path must not persist `disabled` until the dialog resolves (else `[Cancel]` can't truthfully revert). Reuse the `useSettingControl`/settings-panel discipline; no side effects inside React state updaters (StrictMode double-invoke, WP2 lesson).
- **Guard tests must be mutation-proven** — seven WP3.5a guards passed while broken; every safety-critical assertion here protects a delete. Strip comments before source assertions; assert counts not anchored-forward searches; consume production-reported paths.
- **Live verify uses the sandboxed-`$HOME` launch convention** (root `CLAUDE.md`, recorded 2026-07-30): `HOME=<fake> RUSTUP_HOME=… CARGO_HOME=… PATH=… pnpm tauri:dev`, re-staging between runs. Note `src-tauri/target/` was cleaned — first build is a cold multi-minute rebuild.

## Asked / Assumed (elicitation record)

**Asked:** none — every consequential product decision was settled by the operator in the WP3.5 split, the 2026-07-29 script audit, and the WP3.5a handoff.

**Assumed (defaults taken without asking):**
1. `[Uninstall]` **removes the managed clone directory**, not just the symlinks — per the source SURFACE's own words ("download/**remove** the mccc repo"; "a first version that can only CREATE or REMOVE a clone"). Sequence: script → clone dir → record last.
2. **Gate stays disabled after a *failed* uninstall** (the user's disable intent stands; record kept → still `managed` → retry available on next disable; `[Keep mccc]` proves disabled-with-substrate is coherent). Error output surfaced, mirroring the install wizard.
3. **`[Keep mccc]` keeps the provenance record** — substrate remains `managed`, so a later disable re-offers the wizard.
4. **No `--project` flag is ever passed** (out of scope above).
5. **Mid-run cancel of the uninstall**: same posture as install — the run either completes the current atomic step or stops between steps; the record survives unless the full sequence completed. (Exact cancel points are a plan-level decision inside the terminal-state table.)
6. If the recorded clone is **missing or damaged** (no `uninstall.sh`), the refuse-guard refuses and the dialog degrades to explaining the state + offering `[Keep mccc]`/`[Cancel]` semantics only — never a blind delete. (Detail wording at plan/build.)
7. An empty `~/.claudesk/vendor/` left after removal is not cleaned up specially; the record file's deletion is the last act.
8. **The live sandboxed verify-human pass for this WP runs pre-close** (deviates from the WP3.5a deferral precedent, deliberately — see AC 8; flag if you want the deferred batch instead).
9. **An unrecorded leftover clone is never auto-deleted.** A failed install deliberately leaves its clone as a valid retry base (`Cleanup::None`, pinned by a WP3.5a test); the uninstall path must not "helpfully" clean up what no record covers.

## Binding lessons from the WP3.5a raw-log review (2026-07-31)

Mined from the four raw session transcripts (planning/split · WP3 · build · verify-human) at operator direction. Items already reflected in the ACs above are not repeated. **Every build/verify phase of this WP inherits these.**

### Design / correctness
- **Removal logic keys on TARGET-side state, never source-existence.** Upstream proved an `[ -d source ]` guard on a removal path goes permanently false once the source is deleted, silently stranding exactly the installs the cleanup exists to rescue. Predicates for uninstall decisions read the symlinks/record, not whether the installer's source still exists.
- **`RecordWriteFailed` produces installed-but-`Developer` substrates** (install succeeded, record didn't land, gate reverted). The provenance→UI copy (AC 2) must not treat `Developer` as only "the operator's hand-install."
- **Consent/preview copy states conditions, never fixed lists** — both cross-repo handoff docs contained one error each, caught only by re-reading the actual script. **Re-verify every claim against `uninstall.sh` at build time**; don't inherit claims from WBS/handoff prose.

### Verification protocol (destructive-WP hardening)
- **Serialize sessions.** No concurrent Claude session may edit this tree while the deleting path is built or verified. WP3.5a survived a concurrent-session race (foreign mutation planted in production code, files oscillating, tests externally reverted) on the *additive* half; on the deleting half that same race is intolerable.
- **Mutation discipline:** break-the-guard-watch-it-fail on every safety assertion; `touch` after any `cp -p` restore (preserved mtime → cargo reuses a stale test binary — bit three times); three consecutive clean runs as the stability bar; a varying failure count is NOT evidence of flakiness — read the failing assertion's source before classifying; re-run from the current tree before believing any cached subagent failure text.
- **macOS `timeout` does not exist** (exit 127) — use `perl -e 'alarm'`. Bash subshells need `source "$HOME/.cargo/env"`. Strip comments before any source-scan assertion (two WP3.5a scans matched their own prose).
- **Sandboxed-`$HOME` launch specifics:** literal absolute paths in the command handed to the operator (a `$HOME`-referencing form self-defeats); launch the dev build as a **background task** (a foreground chain died at a turn boundary); re-stage between runs by removing **both** fake `.claude/` **and** fake `.claudesk/` (the record keeps it `managed`); check the running binary's mtime against the latest commit before verifying Rust-side behavior.
- **Operator drives live verification; the agent launches and stages.** Label any injected/staged state explicitly when showing it (an unlabeled injected `absent` state read as "the wizard is missing"). Port 1420 occupied at a verify-human gate → **ask, never kill** (the holder was the operator's live app once). Never edit `settings.json` or the provenance record while the app runs — it writes its in-memory state back on exit.
- **Absolute paths only in every Bash command** — `cd` in compound commands failed silently three separate times across the sessions; with a deleting script in play, a wrong cwd is not just waste.

### Process
- **Work THIS WP's task list** — never the frozen pre-split WP3.5 list (reference-only, deliberately unchecked forever).
- **Re-read the module directory on every session re-entry; the code wins over the Work Tree** (WP3.5a rebuilt an already-built phase from a stale `Current Node` and its own memory of "the three files I created").
- **Push back at the moment** the operator picks an option the agent's own preview flagged as dangerous — don't spec around it (the vendor-dir hand-clone-path decision had to be walked back a session later).
- **If the dry-run preview surfaces something wrong-looking, the expected move is a cross-repo ask + pause**, not copy that explains it away (the operator's demonstrated lean, twice).
- The affordance and its expanded form share one position (the twice-misplaced install button); `scrollIntoView({block:"nearest"})`, not `"start"`.
