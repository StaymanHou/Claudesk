## Problem Statement

The workflow-features gate shipped in WP2 and is OFF for everyone, reachable only by a
user who already knows to press `⌘,` and already knows what "workflow features" means. A
secondary Claude Code user has no way to discover the feature class exists, and no way to
learn that it needs a companion install. WP3 builds the on-ramp: a **one-time dismissible
invite** that pitches the layer and routes to Settings, plus the **substrate context** in
Settings itself — is the workflow system installed, how to install it, how to remove it,
and (once installed) the `/tutorial-getting-started` pointer.

**Rescoped 2026-07-29 by operator decision.** The WBS originally had the invite carrying
install commands, running its own presence check, and flipping the gate inline. The
operator moved the boundary: **Settings owns the substrate, the invite owns only
discovery.** So the invite is pitch + route (it opens Settings and highlights the
workflow-features row; it does **not** flip the gate), and all substrate content lives in
Settings. This tightens Verdict (b)'s own scoping rule — the invite's irreducible
non-overlap is *discovery* — which the original task list violated by duplicating install
content into the invite. See `wbs.md` → "Verdict (b) revision — 2026-07-29" + "Settled
copy — 2026-07-29" (copy is operator-approved; this feature implements it, it does not
re-decide it).

**WP3 writes nothing outside Claudesk's own `settings.json`.** The presence check is
read-only `stat`. Running `install.sh`/`uninstall.sh` is **WP3.5's** (the wizards), gated
behind the sandbox discipline `SURFACE-2026-07-28-MCCC-INSTALL-FEATURE-NEEDS-SANDBOXED-DEV-AND-VERIFY`
(**high**) requires. Do not anticipate it here beyond leaving the injectable-root seam.

**No 3rd-party probe needed.** The companion repo is a *documentation* dependency
delivered as static text, not a runtime API (WBS dependency map §4). Its surface contract
was read directly from source this session (`HANDOFF-from-mccc-2026-07-28.md`, the
companion repo's `onboarding-flow-spec.md` §1/§4/§6, `README.md` §Setup) — WP3.1 is
therefore **already discharged**; findings are in "Task 3.1 findings" below.

## Constraints carried in (each one cost real debugging somewhere)

- **Never call a side effect inside a React state updater.** StrictMode double-invokes
  them. This double-wrote every settings toggle in WP2 (caught at review), and is the same
  root cause as WP2's Esc-ordering bug. (`CLAUDE.md:190-192`)
- **`?raw` source-text guards verify STRUCTURE, never RUNTIME.** WP2 paid twice — one guard
  passed while the behavior was broken (source order ≠ execution order), another silently
  stopped matching after a Prettier reflow. Anything involving React batching, async, or
  event ordering is extracted to a **pure function** and asserted as a **value**.
- **Add a settings control via a `useSettingControl` spec** (`get`/`persist`/`event`/
  `errorLabel`) — never by re-copying the seed/listen/optimistic-set/revert discipline.
- **A third app-level overlay joins `escDismissTarget`'s union** — not a third keydown
  listener, and not another `if` in the handler. The module's own header says so.
- **No dimmed backdrop.** Operator decision, test-pinned (`SettingsPanel.tsx` header). The
  invite follows suit — do not add a scrim to either surface without re-asking.
- **The invite must NOT be gated behind `useWorkflowFeaturesEnabled`.** It is the one
  workflow-named surface that exists *precisely when the gate is OFF* — the inverse of the
  seam contract. See P1's note on the OFF-invariant guard.

## Phasing rationale

Four phases, ordered so each is independently verifiable and the risky copy decisions land
last (when they can be judged in the real app):

- **P1 backend first** — the field and the presence check are the substrate everything else
  reads. Both are pure-logic + `TempDir`-testable, so P1 is fully agent-verifiable with no
  live app.
- **P2 pure predicate before any UI** — the show-logic is the part with a truth table and
  the part a naive implementation gets wrong (the disable-after-enable and `[Later]` rows).
  Isolating it means those rows are asserted as values, per the `?raw`-guards lesson.
- **P3 Settings before the invite** — the invite *routes to* Settings, so the destination
  should exist before the thing pointing at it. Also lets the operator judge the substrate
  copy independently of the pitch copy.
- **P4 the invite last** — it depends on P2's predicate and P3's destination, and it is the
  surface whose copy most needs a live human read. Its verify-human carries the three
  judgment calls that can only be made by looking at the real thing.

**Deliberately NOT in scope** (WP3.5's, or later): running `install.sh`/`uninstall.sh`, the
managed clone, the provenance store, the refuse-guard, the three-intent uninstall wizard.
WP3 leaves the injectable-root seam (P1.2) that WP3.5 will need, and nothing more.

[SURFACED-2026-07-29] Phase 3 / verify-self — **a `<pre>` inside a `display: flex` +
`align-items: flex-start` parent will NOT scroll internally, no matter what `overflow-x` it
carries.** The flex child sizes to content, so the element is never constrained and its own
overflow rule is dead; the clipping surfaces on some *ancestor* instead, which is what makes it
hard to attribute. This is a general trap for any future wide content added to a settings group
(a long path, a wide table, a code block) — the fix is `align-self: stretch` + `min-width: 0` on
the wrapper, and the diagnostic is to compare a child's `getBoundingClientRect().width` against
its parent's `clientWidth` rather than trusting the child's own `scrollWidth`. Worth a repo
convention note if a second instance appears; NOT backlogged as its own item yet since the
one occurrence is now fixed and commented at the site.

[SURFACED-2026-07-29] Phase 1 / verify-self — **an Observable Outcome of the form
`cargo test <filter>` is VACUOUS unless it also pins a test count.** Phase 1's outcome 2
named `cargo test -p claudesk skills_present`; that filter matches **zero** tests, and
`cargo test` with a no-match filter **exits 0**. So the outcome would have passed against an
empty codebase — it asserted nothing. Caught by the verify-self subagent (it ran the literal
filter, saw `0 passed; 577 filtered out`, and flagged the mismatch instead of scoring a
silent PASS). Verified empirically both ways before fixing. This is the **same false-pass
shape** as the `?raw` guards that broke twice in WP2 — a check whose *form* looks like
verification while its *content* is empty. Fixed in place (the filter now names the real
module and the outcome asserts "8 passing tests"). **Generalizable rule for future plans:
