# Feature: M10.9 WP3.5a — Sandbox foundation + install wizard

**Workflow:** feature
**State:** ship (complete)
**Created:** 2026-07-29
**Entry:** spec (complex feature)

## Problem Statement

A secondary Claude Code user who wants Claudesk's workflow-orchestration layer currently has to
leave the app: WP3 shows them a status line and three copy-able shell commands, and that is the
entire on-ramp. The milestone's actual value — "a secondary user can get the substrate" — is not
yet deliverable by Claudesk itself.

WP3.5a makes Claudesk able to **install** the companion workflow system: pick a location, clone
the repo, run its `install.sh`, and record what was done. It is the additive, safe half of the
install/uninstall pair (`SURFACE-2026-07-28-MCCC-INSTALL-UNINSTALL-INTERFACE-IN-CLAUDESK`).

It is also the work package that builds the **safety substrate** the destructive half depends on:
an injectable-root sandbox fixture, and a provenance store that records what Claudesk installed.
Both exist so that WP3.5b's deleting paths arrive into a shape that is already sandbox-testable
rather than retrofitted — the explicit demand of
`SURFACE-2026-07-28-MCCC-INSTALL-FEATURE-NEEDS-SANDBOXED-DEV-AND-VERIFY` (**high**).

**Why this is a spec and not a plan-only change:** it introduces a new persisted artifact (the
provenance record) whose location has a hard constraint, spawns two external subprocesses whose
failure modes must map onto a UI gate that can revert, and mutates state outside Claudesk's own
data dir for the first time in the app's history. That last point is a reversal of a milestone
property, not a feature increment.

## Milestone-property revision this feature carries

Milestone property 2 was **revised 2026-07-29** from *"enable touches NOTHING in `~/.claude/`"* to
*"…EXCEPT through an explicit, user-driven wizard."* This WP is the first code to exercise that
exception, so it inherits the burden of keeping the two acts separate:

> **Enabling the gate and installing the substrate remain strictly separate acts.** The wizard is
> a consequence the user opts into, never a silent side effect of the toggle.

Concretely: flipping `workflow_features_enabled` must still write only to Claudesk's own
`settings.json`. The wizard is reached from the Settings substrate block, and its own confirmation
step is what authorizes any `~/.claude/` mutation.

## User Stories

- As a **secondary Claude Code user** who just enabled workflow features and has no substrate, I
  want to install it from inside Claudesk so that I do not have to find a terminal, a repo URL,
  and three commands to get the features I just turned on.
- As **any user about to let an app write into `~/.claude/`**, I want to see every side effect
  named before I consent — including the ones that touch files I did not know were involved — so
  that I can decline on an informed basis.
- As a user whose install **fails** (no network, bad disk, script error), I want the gate to stop
  claiming a substrate that is not there, and I want the real error output, so that I can tell
  what broke instead of being left in a lying UI state.
- As **the operator**, whose `~/.claude/skills/` symlinks point into a companion repo I actively
  edit, I want Claudesk to record what it installed rather than infer it from paths, so that no
  later code path can mistake my live source repo for something it may manage.
- As **the agent developing this**, I want a sandbox fixture with injectable roots before any
  writing code exists, so that verification never runs against the operator's real `~/.claude/`.

## Acceptance Criteria

### Sandbox foundation (3.5.1)

- A test fixture provides **injectable roots** — fake `$HOME`, fake clone parent, fake
  `~/.claude/` — and every test in this feature runs against it.
- The fixture is **proven to contain writes**: a test asserts that after exercising the install
  path against the sandbox, nothing was created outside the fixture's temp roots.
- **No production function in this feature resolves an ambient home directory.** Roots arrive as
  parameters; only the thin `commands` layer resolves real paths. Enforced the way
  `workflow_substrate` already enforces its read-only posture — a standing guard test over the
  module's own source.

### Provenance store (3.5.3, write + read)

- A record is written **at install time**, capturing at minimum: the managed clone path, the
  install timestamp, and the substrate's origin (repo URL / ref).
- **Provenance is never inferred from a resolved filesystem path.** A test pins this: given a
  substrate present on disk with no record, the state resolves to *not managed* — never adopted.
- The record's location is **not bundle-identity-scoped** (see Technical Constraints), so a dev
  build and a prod build read the same record for the same managed clone.
- Three states are distinguishable: **absent** · **managed install** · **developer install**.
  WP3.5a only needs to *write* `managed` and *read* all three to pick the install affordance;
  uninstall consequences are WP3.5b's.
- A corrupt or unreadable record degrades to **not managed** (never to "managed", which would make
  it eligible for a later delete), and never crashes the Settings panel.

### Install wizard (3.5.4)

- Reachable from the Settings substrate block in the **absent** state; not offered in the managed
  or developer states.
- Flow: **location picker** (default `~/.claudesk/vendor/`, user-changeable) → **consent step** →
  `git clone` → `./install.sh` → **record provenance**.
- Real script output is **streamed and surfaced** — the scripts are the source of truth for what
  happened. Claudesk does not re-implement, summarize, or paraphrase their logic.
- On success, the substrate block re-resolves to the **managed** state without requiring a relaunch.

### Consent copy (3.5.4b)

Names every side effect, specifically:

- per-**skill** and per-**agent** symlinks created under `~/.claude/`;
- the marker-delimited block injected into the user's **global `~/.claude/CLAUDE.md`**, and the
  **`.bak`** backup taken when that file already exists;
- the four `permissions.allow` entries the script **prints but never applies** — the user must add
  them by hand.
- **Created directories are stated conditionally, never as a fixed list**: `~/.claude/bin/` is
  never created; `~/.claude/hooks/` is created *only if* the companion repo ships a `hooks/`
  directory (it currently does not — `install.sh:67-68` is live-but-dormant code). A hardcoded
  list would go stale the moment upstream adds one.

### Install-half terminal states (3.5.6a)

- Modeled in a **pure module** and unit-tested **as a table**, asserting values — never a `?raw`
  source guard (root `CLAUDE.md`: async control flow with revert semantics is exactly the class
  that must be a pure function asserted as a value; WP2 paid twice for getting this wrong).
- Cases covered, each with its required outcome:

| Terminal state | Gate | Substrate | Surfaced |
|---|---|---|---|
| clone fails (network, auth, bad URL) | **reverts to OFF** | nothing left behind | real `git` stderr |
| `install.sh` exits non-zero | **reverts to OFF** | whatever the script left (it is idempotent — a retry repairs) | real script output |
| disk full mid-clone | **reverts to OFF** | partial clone **cleaned up** | real error |
| user cancels mid-run | **reverts to OFF** | **no half-clone left**, or cleaned up and said so | cancellation stated |
| success | ON | managed install recorded | success + install output |

- The invariant the table exists to protect: **the gate is never left ON claiming a substrate that
  is not there.**

### Clone-path display (resolves `SURFACE-2026-07-29-QUALITY-WP3-OPERATOR-SPECIFIC-CLONE-PATH`)

- The developer-install row's hand-run commands show a **neutral** clone path
  (`~/dev/my-claude-code-customization`) with a "clone anywhere you intend to edit it" note —
  replacing WP3's hardcoded `~/Personal/projects/…` (`WorkflowSubstrateInfo.tsx:63`).
- The wizard's `~/.claudesk/vendor/` default is **separate and not mentioned** in that row. The two
  paths deliberately **disagree**: a developer install lives where you edit it; the vendor dir
  lives where you do not. (Decided 2026-07-29 — see Asked #1.)

### WP3 copy that becomes false (3.5.4-adjacent)

Two shipped strings assert Claudesk installs nothing. Both must change when the wizard lands:

- `SettingsPanel.tsx:314` — "Turning this on only shows the features — it doesn't install
  anything." Its own source comment already flags itself for this revisit.
- `WorkflowInviteModal.tsx:44` — "It needs a one-time install outside Claudesk." The install is no
  longer necessarily outside Claudesk.
- `workflowInviteCopy.test.ts` carries a comment marking itself as the thing to revisit; the copy
  tests must be re-pointed, not deleted.

### Verification posture (3.5.7a)

- Verified against the **sandbox**, agent-driven.
- The **live install against the operator's real `~/.claude/` is operator-only**, at verify-human /
  the `/release` gate per `[[installed-build-verify-deferred-to-release]]`. An agent session must
  **never** drive a real install against the operator's home.

## Out of Scope

- **The uninstall wizard, the refuse-guard, and `--dry-run`-driven preview** — all WP3.5b. This WP
  writes no deleting path at all, which is what makes it the safe half.
- **Update semantics.** Settled: option A, install/uninstall only. No `git pull`, no update path,
  no version checking of the substrate.
- **The 3-intent disable dialog** (`[Uninstall]` / `[Keep mccc]` / `[Cancel]`) — WP3.5b. Until it
  lands, disabling the gate flips the gate only, which is exactly `[Keep mccc]`'s behavior and a
  coherent intermediate state.
- **Adopting an unrecorded substrate found inside the managed dir.** Would require inferring
  provenance from a resolved path — the precise thing the high-priority SURFACE forbids. See
  Assumed #4 for the fallthrough.
- **Changing anything in the companion repo's scripts.** Claudesk runs them as-is and surfaces
  their output; it does not patch, wrap, or correct their behavior.
- **Gating `hook_install`.** It is universal (10 generic CC lifecycle events powering status dots
  for any CC user) and keeps running regardless of this feature.
- **A `--with-claude-time` flag.** No such flag exists — the companion repo retired
  `tools/claude-time/` entirely (2026-07-29), so the wizard passes no flag.

## Technical Constraints

### The provenance record's location — the one constraint that dictates its own answer

The record **cannot live in the per-identity `settings.json`**. `~/.claudesk/vendor/` is not
bundle-identity-scoped, so `com.claudesk.app` and `com.claudesk.app.dev` share one clone and must
read one record. Splitting the record per-identity would let the dev build believe a clone is
unmanaged while prod believes it is managed — divergent views of one directory, in a feature whose
whole safety model is "only touch what we recorded."

Consequence: the record lives **alongside the managed clone's own root** (`~/.claudesk/`), not in
either app-data dir. This is a technical/architecture decision → recorded in `arch.md` at ship, not
in `design-priors.md`.

### Module placement is enforced, not merely intended

`workflow_substrate` carries a standing guard test forbidding its production code from mentioning
`remove_dir`, `Command`, `git`, or `install.sh` — the read-only posture that made WP3 provably
non-writing. **The wizard's code therefore lands in its own module** and extends
`workflow_substrate`'s injectable-root *seam* without moving into that module. Adding an ambient
`home_dir()` anywhere in the feature is forbidden by the same SURFACE.

### The scripts do more than the WBS originally assumed (audited 2026-07-29 against the real files)

1. **`install.sh` mutates the user's global `~/.claude/CLAUDE.md`** (`install.sh:102-171`) —
   injects a marker-delimited block, replacing it if markers exist, else **appending** with a
   `.bak` backup, else creating the file. A scope surprise the WBS never mentioned → disclosed in
   consent copy.
2. **`install.sh` prints but never applies** four `permissions.allow` entries (`:176-181`) → the
   consent copy must say the user adds them by hand.
3. **`install.sh` is idempotent** — a retry after a partial failure repairs rather than duplicates.
   This is why a non-zero exit need not roll back the filesystem, only the gate.
4. **`~/.claude/hooks/` is created conditionally** (`:67-68`), `~/.claude/bin/` never. Do not
   enumerate created dirs as a fixed list.

### Existing seams to reuse (do not build new paths)

- **Subprocess spawn:** six modules already use `std::process::Command`
  (`git_diff`, `git_status`, `updater`, `finder`, `sublime`, `env_path`).
- **Streamed output → frontend:** the `cc_session` pattern (`mod.rs:581-587`) — emit chunks on an
  output event, then an exit event.
- **PATH for spawned processes:** `env_path` already sets the login-shell PATH process-wide at
  setup, so `git` resolves in an installed `.app`. Do **not** add a per-spawn PATH hack.
- **Location picker:** `tauri-plugin-dialog` is already a dependency and initialized
  (`lib.rs:145`).
- **Settings control discipline:** supply a `useSettingControl` spec — never re-copy the
  seed/listen/optimistic-set/revert logic.
- **Gate consumption:** read `useWorkflowFeaturesEnabled`; never `invoke` the gate command ad hoc
  (the OFF-invariant guard's bypass scan fails any other call site).

### No 3rd-party probe required (§2)

The companion repo is a **local documentation + script dependency**, not a network API with
unverified I/O shapes. Its two scripts were read end-to-end and audited against the WBS's
assumptions (three corrections recorded above). `git clone` reaches GitHub, but as an ordinary
subprocess whose failure is a non-zero exit + stderr — modeled in the terminal-state table, not an
API contract needing a spike. **No probe WP is needed.**

### Verification reality

Per the repo convention, backend-lifecycle outcomes (subprocess spawn, filesystem mutation) are not
observable from a bare Vite browser. The agent's tier is: sandbox unit/integration tests +
`tsc --noEmit` + `eslint` + `vite build` + a wiring trace, then the MCP bridge for the live UI
(wizard opens, states render, output streams). The **real install** is carried to verify-human.

### Assumed (defaults taken without asking — the review backstop)

1. **Provenance record location** — alongside the managed clone under `~/.claudesk/`, dictated by
   the non-identity-scoping constraint. Technical, not a product-design call → `arch.md`, not a prior.
2. **Consent is a step inside the wizard, not a separate pre-dialog.** One flow, one confirmation

5. **A failed `install.sh` does not roll back the filesystem** — only the gate. The script is
   idempotent, so a retry repairs; an attempted rollback would be Claudesk re-implementing
   uninstall logic inside the *install* WP, which is both out of scope and the destructive path
   this WP exists to avoid.
6. **`git clone` uses the default branch at clone time.** No pinned ref, no version negotiation —
   consistent with the settled install/uninstall-only update semantics.
7. **Progress surfacing reuses the `cc_session` emit shape** (output event + exit event) rather
   than a new streaming mechanism.
8. **The three WP3 copy strings are edited, not deleted**, and their tests re-pointed — the copy
   tests are the upstream-constraint guards (`~10–15 min`, `/tutorial-getting-started`), so
   deleting them would drop the pins along with the stale sentences.

## Work Tree

**Phasing rationale.** The order is dictated, not chosen: the high-priority SURFACE requires the
sandbox fixture to exist and be *proven to contain writes* before any writing code is built. So
Phase 1 is the fixture plus the provenance store — the only two things that can be built without a
subprocess — and it ends with a test proving containment. Phase 2 adds the two spawns behind that
fixture. Phase 3 is the pure terminal-state table (deliberately *after* the spawns exist, so the
table models real observed failure shapes rather than imagined ones). Phase 4 is the UI. Phase 5 is
the copy that becomes false, isolated so a copy edit never rides along with a subprocess change.

## Phase 2 verify-self — 1 BLOCKING found and FIXED (2026-07-29)

**The finding (subagent, then independently reproduced by me):** outcome 1's containment assertion
was **tautological**. `a_successful_run_clones_installs_and_records` asserted
`assert_writes_stay_under(root, &[dest])` where `dest` was the test's **own literal** — comparing
two test-constructed paths, which is constant-true regardless of what production does.
`ok.record.clone_path` laundered the same tautology (it is built *from* the `dest` parameter, not
observed from disk).

**Proven, not assumed.** I made production clone to `/tmp/claudesk-escaped-clone` and symlinked
`dest` at it: the test **PASSED** while real directories landed outside the sandbox. This is the
highest-value defect in the module so far, because WP3.5b's *deleting* code will inherit these
assertion patterns — a containment check that cannot fail is worse than none, since it reads as
proof.

**The fix (3 parts):**
1. `InstallSuccess` gained **`cloned_to`** — where the clone *actually* landed, read back via
   `canonicalize()` after the clone. Production now reports an **observation**, not an echo.
2. The test asserts on `ok.cloned_to`, never on `dest`.
3. Two new meta-tests: `the_containment_assertion_fails_when_production_reports_an_escaping_path`
   and `the_reported_clone_path_is_an_observation_not_an_echo_of_the_argument` (passes a `..`-laden
   `dest` and requires the reported path to differ — only a real `canonicalize` collapses it).

**Re-verified by re-applying the original escape:** the mutation that previously passed now FAILS
with `the clone escaped the injected root: production cloned to "/private/tmp/..."`. The
canonicalization is what defeats the symlink laundering.

**Two collateral fixes the canonicalization forced:**
- **`sandbox.rs` gained `canonical()`, applied to BOTH sides of every containment comparison.** On
  macOS `TempDir` sits under `/var/folders/…` and `/var` is a symlink to `/private/var`, so a
  production-canonicalized path compared as an *escape* against the non-canonical boundary — a
  false BLOCKING the first time a real production path met these asserts. Canonicalizing both sides
  does not weaken the check; resolving symlinks is precisely what closes the link-based escape.
- **`early_output_reaches_the_sink_before_the_script_exits` re-based onto the GAP between the two
  observations** instead of the first one's absolute wall-clock. It flaked at 1151ms against a
  1000ms threshold once this module's test count grew: the number is dominated by scheduler wait,
  not pipe latency, so the documented 159–228ms was real but not a stable budget. The gap is
  load-invariant (streaming separates the lines by ~SLEEP_SECS; buffering collapses it to ~0)
  because scheduling delay shifts both timestamps together and cancels.

**Also carried forward from the subagent (not blocking):**
- **COSMETIC:** no test composes a real `run_install` with `resolve_state` to prove `state ==
  managed` end-to-end; it holds by composition (the record is proven present + readable, and
  `resolve_state(true, Some(_)) => Managed` is a total arm). Worth closing at verify-codify.
- **`run_streaming` does NOT stream stderr** — it is drained on a thread and replayed *after*
  `wait()`, so the module doc comment's "one interleaved transcript in the order things actually
  happened" is inaccurate. Verbatim delivery (the plan's actual outcome) still holds. **Fix the
  comment or the behavior at Phase 4**, when the wizard surfaces this output for real.
- **Cancel is polled synchronously between steps**, so a cancel arriving *during* a long clone is
  not honored until the clone finishes. Deliberate and documented, but the wizard's Cancel button
  will feel unresponsive during the slowest part of a real install — **Phase 4 UI must account for
  this** (disable/relabel rather than implying instant cancellation).

  designed. **This is a real coverage gap worth knowing**: containment is asserted on *constructed
  paths*, so a path that is inside the root but *resolves* outside it is invisible. A future
