## Milestone intent (read before scoping any WP)

M10.9 decides **how a secondary Claude Code user who does NOT run the custom workflow system experiences Claudesk.** It is an *audience-boundary* feature, not a feature-flag chore. Three properties carry the whole milestone:

1. **OFF = byte-identical** to a Claudesk that never had workflow features. No empty tabs, no greyed controls, no dead menu items, no live chords. This is the load-bearing invariant — it's what makes "no design concession" honest rather than "a worse default for them."
2. **Enable = a pure Claudesk UI-state flip that touches NOTHING in `~/.claude/`.** The operator's skills are live symlinks into the companion repo they actively edit; an install-on-enable step would risk clobbering that source. "Enable the UI" and "install the substrate" are strictly separate acts.
3. **The invite is evangelistic, not a nag.** Shown once while OFF, dismissible, and it *converts* a hard audience boundary into a soft discoverable one — at zero cost to the primary experience.

## ⚠️ Baseline finding that shapes this WBS (audited 2026-07-28)

**Nothing currently shipped is workflow-coupled.** A full inventory of `src/` + `src-tauri/src/` found **zero** user-facing surfaces that depend on the workflow substrate:

- No workflow-file reader anywhere. The only one ever scheduled — M3 WP5's `.session.md` watcher — was **dropped** (CHANGELOG:437, "the wrong signal").
- `RightPanel` is a 3-member union (`editor|diff|terminal`); no `"docs"` member exists, so there is no empty Docs tab today.
- Not one live `⌘⇧` chord is workflow-coupled. No skill buttons, no Recycle Session, no slash-command injection UI.
- No read of `~/.claude/skills/` anywhere.
- `hook_install` (the only `~/.claude/` writer) is **universal, not workflow-coupled** — it registers 10 *generic CC lifecycle* events that power the status dots for any CC user. It must keep running with the gate OFF.
- The time-analytics dashboard is **universal** (roadmap line 156 verified against code: generic hook events, workflow-agnostic segment kinds). Its own `time_tracking_enabled` flag is the correct and sufficient gate; M10.9 does **not** gate it. It is in fact the *template* for this milestone's flag.

**Consequence — the OFF=byte-identical invariant is already true of the current build, so there is NO de-wiring work.** M10.9 is therefore *not* "hide a bunch of existing UI." It is: establish the gate + its consumption seam **before** M11 becomes the first consumer, build the Settings surface needed to reach it, and build the invite/on-ramp. This inverts the naive sizing — the gate plumbing is small (WP2, S) and the *on-ramp* is where the milestone's weight and risk actually sit (WP3+WP4).

**The one genuine workflow artifact found:** `Project::default_drive_mode` (`config_store/mod.rs:53`) — a reserved, UI-less, round-trip-tested field. Not user-facing ⇒ not gated (leaving it is byte-identical from the user's view). Noted so a later audit doesn't re-discover it as a gap.

## Cross-repo seam (the constraint that governs WP3/WP4)

Per the return contract's **§4c anti-brittleness clause**, the **ONLY** stable coupling Claudesk may depend on is the command name **`/tutorial-getting-started`**. Claudesk must **NOT** hardcode:

- the tour's flow, steps, beats, or copy;
- the greenfield/brownfield path choice (the fork happens *inside* the entry skill — Claudesk must not pre-select);
- the permission-mode instruction (mode guidance is delivered by the skill, not invite copy).

That clause is *proven*, not asserted: the companion repo's mode recommendation changed `acceptEdits` → `auto` mid-cycle with **zero** Claudesk changes. Preserving it keeps mode guidance a one-repo edit forever.

**Also binding — the honest-framing invariant:** the tour is a **narrated real run of ~10–15 minutes** that really executes things and writes files. The companion spec **forbids** promising a "quick 5-minute" tour and structurally pins that. **Invite copy must not promise a 5-minute demo.** If a shorter value-prop line is wanted, the handoff asks us to *request* one rather than author it (§"What the workflow repo needs back", courtesy 2).

## Design-prior consult

- **`[[gate-substrate-dependent-feature-class-behind-default-off-opt-in]]`** — directly on-axis; this milestone *is* the prior's origin. **Rule 2 (prior agrees with the common-sense default)** → taken with high confidence, no override. It settles three things that would otherwise be re-litigated per-WP: (a) **default OFF for everyone including the operator** — set by *applicability* (the features have nothing to act on without the substrate), explicitly **not** by audience size, a candidate rule the operator rejected 2026-07-20; (b) **no environment auto-detection** — same code path for all users, the operator accepts a one-time conscious enable; (c) the corollary constraints that OFF be *byte-identical* and enable be a pure app-state flip touching nothing in `~/.claude/`.
- **`[[new-surface-must-earn-its-place-against-existing-ones]]`** — fired on the **Settings surface** question (WP1). - **`[[explicit-selectable-mode-over-inferred-mode]]`** — supports the boolean-with-visible-toggle shape over any inferred/auto-detected enablement.

No new design prior proposed — M10.9's decisions are applications of the existing gate prior (whose why is already recorded from this milestone's own design discussion), not a new transferable lean. *(A capture checkpoint remains open at WP1's Settings-surface call and WP3's invite-copy call — if the operator's reasoning there reveals a transferable lean, propose it then.)*

### Verdict (b) — Invite trigger + persistence

**Trigger:** **first launch at which the picker renders with ≥1 project in `list_projects`**, while the gate is OFF and the invite has never resolved. *Not* first-launch-unconditionally. Reason: a genuinely fresh install lands on the picker with **zero** projects (`read_settings` returns defaults when `settings.json` is absent — `settings.rs:99-111` — and the recents list starts empty), so an unconditional first-launch trigger pitches a *workflow-orchestration layer for your projects* to a user who has not yet opened a project. The pitch has no referent at that moment, and the invite is the milestone's one shot (it never re-shows). Waiting for ≥1 project costs nothing — the user reaches that state within seconds of their first "Open Folder…" — and the pitch then lands against something concrete. **Where `projectCount` comes from — settled here so WP3 doesn't have to improvise (added at review-quality, 2026-07-28).** An earlier draft of this verdict claimed the trigger "requires no new IPC" because `ProjectPicker` already holds `recents` from `list_projects` (`ProjectPicker.tsx:146`). That is true of the *picker* but **incompatible with hosting the invite at the app shell**: `list_projects` is invoked **only** in `ProjectPicker.tsx`, and `App.tsx` holds no project-list or count state (both verified 2026-07-28). The two decisions were jointly unrealizable as written.

**Resolution:** `App.tsx` does its **own** `list_projects` invoke for the count — a second call site, accepted deliberately. Rationale: (a) it is a cheap read of a ≤100-entry JSON file, already re-invoked on every picker mount, so a second call is not a cost worth designing around; (b) the alternatives are worse — lifting `recents` into a shared store is real refactoring of a working surface for one boolean's benefit, and prop-drilling a count *up* from the picker inverts the ownership (the invite must be able to fire on a scene the picker does not own); (c) it keeps the invite genuinely app-level, which is what verdict (a)'s strip retirement requires. **WP3 must gate this read on `workflow_invite.is_none()`** so the extra IPC is skipped entirely once the invite has resolved — which is permanently, for all but first-run users.

**AppSettings field(s):** one new field —
```rust
/// M10.9 — has the one-time workflow-features invite resolved, and how.
/// `None` = never shown yet (the only state that permits showing it).
#[serde(default, skip_serializing_if = "Option::is_none")]
pub workflow_invite: Option<WorkflowInviteOutcome>,
```
with
```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "kebab-case")]   // → "dismissed" | "enabled"
pub enum WorkflowInviteOutcome { Dismissed, Enabled }
```
Follows the established optional-with-default + `rename_all = "kebab-case"` enum shape (`PipMode`, `pip/layout.rs:43-55`; `CcPermissionMode` uses explicit per-variant renames for CLI fidelity, which does not apply here). **Field-count bookkeeping (corrected at verify-self, 2026-07-28):** `AppSettings` currently carries **7** fields (`pip_layout`, `pip_mode`, `cc_permission_mode`, **`cc_yolo`**, `time_tracking_enabled`, `update_notifications_enabled`, `skipped_version`), of which only **5** are user-facing preferences — `cc_yolo` is a dead legacy field (retained purely so a pre-dropdown `settings.json` round-trips; never written, `skip_serializing_if` self-cleans it) and `skipped_version` is updater bookkeeping, not a preference. So M10.9's two fields land as the **8th and 9th** fields on the struct, and `workflow_invite` is the **9th field but not a user-facing setting either** (it is a lifecycle marker, invisible in the Settings panel — only `workflow_features_enabled` becomes a visible 6th user-facing setting). *An earlier draft of this verdict said "7th field / 6th user-facing" by omitting `cc_yolo` from the count; corrected here.* Note it is deliberately **separate from `workflow_features_enabled`** — the gate is *current state*, the invite outcome is a *one-time lifecycle marker*; conflating them is what breaks the disable case below.

**Default:** `None` (absent from `settings.json` — so an existing install and a fresh one both read "never shown", which is correct for a brand-new feature).

**Re-suppression:** the show-predicate is **`workflow_invite.is_none() && !workflow_features_enabled && project_count >= 1 && !dismissed_this_session`**. The persisted term is `is_none()`; the session term is React state only (never written to disk).

**Three buttons, three intents (operator-corrected at verify-human, 2026-07-28 — supersedes an earlier two-button `[Enable]`/`[Not now]` draft).** The earlier draft defined `[Not now]` as *permanent* suppression, which is a **mislabeled control**: a button reading "Not now" that means "never again" lies to the user. The operator's model is three genuinely distinct intents, and the middle one is what makes the persistence model coherent:

| Button | Persisted write | Effect |
|---|---|---|
| **`[Install & enable]`** (or `[Enable]` when the substrate is already present) | `workflow_invite = Some(Enabled)` + gate ON | Features on; never re-shown. |
| **`[Later]`** | **none — deliberately writes nothing** | Hidden for *this session only*; **re-shows on next launch**. |
| **`[Dismiss]`** | `workflow_invite = Some(Dismissed)` | Never re-shown. The "done, stop asking" exit. |

`[Later]` is the *absence* of a write — pure React state, mirroring the updater's `dismissBanner` (`useUpdater.ts:180-183`, which clears the banner with `setBanner(null)` and persists nothing, so it reappears next launch) exactly as `[Dismiss]` mirrors `skipVersion` (`:173`, which writes `skipped_version` to disk for permanent suppression). **That precedent is the reason `[Later]` needs no new field** — the existing `None` state already means "unresolved," and a session-scoped hide is a React concern, not a persistence one.

**Consequence — the enum variants ARE load-bearing, not diagnostics.** *(This reverses a line in the earlier draft.)* With a real `[Later]`, the three arms differ by *which write happens, or doesn't*: `None` (re-showable) vs `Some(Dismissed)` vs `Some(Enabled)`. WP3 must branch on that distinction — it is the feature, not bookkeeping.

**`workflow_invite` is internal state, not a user-facing setting** (operator-confirmed at verify-human). It gets **no control in the Settings panel** — it is written only by the invite's own three buttons and read only by the show-predicate. The Settings panel exposes exactly one new *setting*, `workflow_features_enabled`; the invite's lifecycle is invisible there. So M10.9 adds 2 struct fields but only **1** visible setting.

This is what settles the **disable-after-enable case**, which a naive `workflow_invite_seen: bool` handles only by accident and a "derive it from the gate" approach gets actively wrong: a user who enables the features, tries them, then disables returns to `workflow_features_enabled == false` — the *same* gate state as a user who never saw the invite. With the outcome recorded separately, `workflow_invite == Some(Enabled)` suppresses forever and they are not re-pitched something they already evaluated and rejected. **Once `workflow_invite` is `Some(_)`, suppression is permanent and one-directional — nothing in the product ever resets it** (no "show me that invite again" affordance — out of scope; the Settings panel is the durable route to the gate). `[Later]` is not an exception to this: it never writes, so it never enters the suppressed state in the first place.

**Dev re-drive:** a **`window.__workflowInviteReset()`** frontend seam registered **only** under `import.meta.env.DEV`, mirroring the two existing dev seams exactly — `window.__seedWorkspace` (`App.tsx:498-514`) and `window.__editorSynthetic` (`EditorSplit.tsx:463-476`) — declared as an optional member on `Window` in `src/vite-env.d.ts` so the type reflects its absence in production. It writes `workflow_invite: None` through the same setter the invite uses, so WP5 can re-drive the first-run path repeatedly without hand-editing `settings.json`. Chosen over a `#[cfg(debug_assertions)]` Rust command (the other available precedent — `lib.rs:152`, the MCP bridge) because the reset is pure app state with no native surface, and the frontend seam is what the MCP-bridge verify-self path can call directly via `webview_execute_js`. **Neither path exists in a `pnpm tauri build` bundle.**

**Invite host — the now-fired "Also confirm" clause.** WBS 1.(b) asked to confirm the invite has a home that isn't the picker *if* (a) landed on option (iii). It did (**iii-b**), and that verdict **retires the picker settings strip** — so the invite is **its own app-level component**, not a strip row. It follows the `GlobalDashboard`/updater precedent: rendered at the app shell's top level (`App.tsx`) so it overlays whichever scene is up, `import`ed lazily is unnecessary (it is small and shows at most once). **The primary button flips the gate inline** via the WP2 setter and writes `workflow_invite = Some(Enabled)` — it does **not** deep-link into the Settings panel, because making the user find a control to complete an action they already consented to is a pointless second step; the panel remains the route for *later* changes. The three buttons and their writes are tabulated under **Re-suppression** above. **Modal-vs-banner:** a **modal overlay**, matching the updater's confirm dialog rather than its in-flow notify banner — it asks a question and should not be scrolled past unnoticed, and `[Later]`/`[Dismiss]` give two cheap exits so the modality is not a trap. Shown at most once per session and (absent `[Later]`) once per install, so the interruption cost is paid a single time.

**Open sub-question deferred to WP3.2 (copy/labels, not architecture):** whether the primary button reads **`[Install & enable]`** when `~/.claude/skills/` is absent versus plain **`[Enable]`** when it is present — the operator's phrasing was "install if not yet & enable", which is one *intent* whose honest label depends on the WP3.4 presence check. **This does not change the persisted state** (`Some(Enabled)` either way), so it is a labeling decision for WP3.2 alongside the rest of the copy. **Caveat for WP3.2:** the presence check is *soft and read-only* — Claudesk must **not** actually run `install.sh` or write anything into `~/.claude/` (milestone property 2), so a literal "install" button must not promise an action the app is forbidden to take. The safe resolution is a primary button that enables + surfaces the install instructions when the substrate is missing (which is exactly what WP3.5's soft note already does).

**Invite scoping (`new-surface-must-earn-its-place`, per the WBS design-prior consult):** the invite's irreducible non-overlap with the Settings panel is **discovery** — it reaches a user who does not know the feature class exists. So it is scoped to *pitch + install instructions + the three buttons* and must **not** grow into a second settings panel (no mirrored toggles for other settings, no "configure now" sub-flow). Copy constraints are WP3.2/WP3.3's (§4c: name only `/tutorial-getting-started`; never promise a 5-minute tour).

**Suggested implementation shape for WP3** (not a new decision — the pattern this codebase already uses): put the show-predicate in a **pure module** (`shouldShowWorkflowInvite(settings, projectCount)`) mirroring `updater/updateNotifyState.ts`'s `shouldAutoNotify` — no React, no `invoke`, so the suppression truth-table is unit-testable without a running app. That module is the natural home for WP3's tests and makes the disable-after-enable case a one-line assertion.

**State-discipline `workflow_features_enabled` must clone** (read at WP1, verified against the as-built code — WP2 follows this exactly, no invention):

- **Backend field** — `AppSettings` (`src-tauri/src/config_store/settings.rs:37-97`) is a flat all-`Option` struct; every field carries `#[serde(default, skip_serializing_if = "Option::is_none")]` so an older/fresh file round-trips forward-stably. `time_tracking_enabled` (`:68-77`) is the closest template: `Option<bool>`, default applied by the **reader** (`read_time_tracking_enabled:199`) not by serde, with a read-modify-write setter (`write_time_tracking_enabled:207`) that preserves the other fields.
- **Frontend seed + sync + optimistic-set + revert** — the picker runs this triple three times over (`ProjectPicker.tsx`: permission mode `:164-202`, time tracking `:209-250`, update notifications `:253-330`). The shape: on mount, `invoke` the getter and `setState` (guarded by a `cancelled` flag for StrictMode), `listen()` to the broadcast event so *any* mirror surface flipping the value re-syncs this control, then on user change do an **optimistic** `setState` → `invoke` the setter → **revert to the prior value + error toast** via `mapIpcError` on rejection.
- **Menu mirror** — handles to the `CheckMenuItem`s are stashed in Tauri managed state at build time (`app_menu/mod.rs:87-91` `PipModeMenuItems`, `:122-124` `CcPermissionModeMenuItems`) because **there is no menu-rebuild path**; a broadcast listener wired in `lib.rs` calls `apply_pip_mode_to_menu` / `apply_cc_permission_mode_to_menu` (`:99`, `:131`) to re-check them. A boolean gate needs one `CheckMenuItem` and the same stash+apply pair.
- **Id byte-identity** — the menu item's id string must be added to Rust `ids` + `FUNCTIONAL_IDS` (`app_menu/mod.rs:186-208`) **and** to TS `MENU_IDS` (`src/menu/menuBridge.ts:26-56`) byte-for-byte; an existing test greps that every `FUNCTIONAL_IDS` entry appears as a quoted `MENU_IDS` value (`:516-537`). `menuActionFor` then maps the id to either a synthetic `keydown` or a named React callback seam (`menuBridge.ts:72-98`) — a gate toggle is a **callback**, not a key (it has no chord, and per the WBS's OFF-invariant no workflow chord may exist while OFF).
