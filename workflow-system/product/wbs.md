## Milestone intent (read before scoping any WP)

M10.9 decides **how a secondary Claude Code user who does NOT run the custom workflow system experiences Claudesk.** It is an *audience-boundary* feature, not a feature-flag chore. Three properties carry the whole milestone:

1. **OFF = byte-identical** to a Claudesk that never had workflow features. No empty tabs, no greyed controls, no dead menu items, no live chords. This is the load-bearing invariant — it's what makes "no design concession" honest rather than "a worse default for them."
2. **Enable = a pure Claudesk UI-state flip that touches NOTHING in `~/.claude/` — EXCEPT through an explicit, user-driven wizard.** *(REVISED 2026-07-29 by operator decision; supersedes the original absolute form.)* The gate itself is still pure app state: flipping `workflow_features_enabled` writes only to Claudesk's own `settings.json`. What changed is that Claudesk **may** install and uninstall the substrate — via an **install wizard** on enable (the user chooses the download location) and an **uninstall wizard** on disable — because the operator asked for it (`SURFACE-2026-07-28-MCCC-INSTALL-UNINSTALL-INTERFACE-IN-CLAUDESK`). The original fear (clobbering the operator's live symlinks into the companion repo they actively edit) is addressed by **provenance** rather than by abstinence: Claudesk only uninstalls what Claudesk recorded installing, and the uninstall wizard asks explicitly rather than inferring. **"Enable the UI" and "install the substrate" remain separate acts** — the wizard is a *consequence* the user opts into, never a silent side effect of the toggle. This capability is **WP3.5's**, gated behind the sandbox discipline that `SURFACE-2026-07-28-MCCC-INSTALL-FEATURE-NEEDS-SANDBOXED-DEV-AND-VERIFY` (**high**) requires; WP3 itself stays read-only.
3. **The invite is evangelistic, not a nag.** Shown once while OFF, dismissible, and it *converts* a hard audience boundary into a soft discoverable one — at zero cost to the primary experience.

## ⚠️ Baseline finding that shapes this WBS (audited 2026-07-28)

**Nothing currently shipped is workflow-coupled.** A full inventory of `src/` + `src-tauri/src/` found **zero** user-facing surfaces that depend on the workflow substrate:

- No workflow-file reader anywhere. The only one ever scheduled — M3 WP5's `.session.md` watcher — was **dropped** (CHANGELOG:437, "the wrong signal").
- `RightPanel` is a 3-member union (`editor|diff|terminal`); no `"docs"` member exists, so there is no empty Docs tab today.
- Not one live `⌘⇧` chord is workflow-coupled. No skill buttons, no Recycle Session, no slash-command injection UI.
- No read of `~/.claude/skills/` anywhere.
- `hook_install` (the only `~/.claude/` writer) is **universal, not workflow-coupled** — it registers 10 *generic CC lifecycle* events that power the status dots for any CC user. It must keep running with the gate OFF.
- The time-analytics dashboard is **universal** (roadmap line 156 verified against code: generic hook events, workflow-agnostic segment kinds). Its own `time_tracking_enabled` flag is the correct and sufficient gate; M10.9 does **not** gate it. It is in fact the *template* for this milestone's flag.

**Consequence — the OFF=byte-identical invariant is already true of the current build, so there is NO de-wiring work.** M10.9 is therefore *not* "hide a bunch of existing UI." It is: establish the gate + its consumption seam **before** M11 becomes the first consumer, build the Settings surface needed to reach it, and build the invite/on-ramp. This inverts the naive sizing — the gate plumbing is small (WP2, S) and the *on-ramp* is where the milestone's weight and risk actually sit (WP3+WP4).

**The one genuine workflow artifact found:** `Project::default_drive_mode` (`config_store/mod.rs:53`) — a reserved, UI-less, round-trip-tested field. Not user-facing ⇒ not gated (leaving it is byte-identical from the user's view). Noted so a later audit doesn't re-discover it as a gap.

## Cross-repo seam (the constraint that governs WP3/WP4)

Per the return contract's **§4c anti-brittleness clause**, the **ONLY** stable coupling Claudesk may depend on is the command name **`/tutorial-getting-started`**. Claudesk must **NOT** hardcode:

- the tour's flow, steps, beats, or copy;
- the greenfield/brownfield path choice (the fork happens *inside* the entry skill — Claudesk must not pre-select);
- the permission-mode instruction (mode guidance is delivered by the skill, not invite copy).

That clause is *proven*, not asserted: the companion repo's mode recommendation changed `acceptEdits` → `auto` mid-cycle with **zero** Claudesk changes. Preserving it keeps mode guidance a one-repo edit forever.

**Also binding — the honest-framing invariant:** the tour is a **narrated real run of ~10–15 minutes** that really executes things and writes files. The companion spec **forbids** promising a "quick 5-minute" tour and structurally pins that. **Invite copy must not promise a 5-minute demo.** If a shorter value-prop line is wanted, the handoff asks us to *request* one rather than author it (§"What the workflow repo needs back", courtesy 2).

### Verdict (b) — Invite trigger + persistence

**Trigger:** **first launch at which the picker renders with ≥1 project in `list_projects`**, while the gate is OFF and the invite has never resolved. *Not* first-launch-unconditionally. Reason: a genuinely fresh install lands on the picker with **zero** projects (`read_settings` returns defaults when `settings.json` is absent — `settings.rs:99-111` — and the recents list starts empty), so an unconditional first-launch trigger pitches a *workflow-orchestration layer for your projects* to a user who has not yet opened a project. The pitch has no referent at that moment, and the invite is the milestone's one shot (it never re-shows). Waiting for ≥1 project costs nothing — the user reaches that state within seconds of their first "Open Folder…" — and the pitch then lands against something concrete. **Where `projectCount` comes from — settled here so WP3 doesn't have to improvise (added at review-quality, 2026-07-28).** An earlier draft of this verdict claimed the trigger "requires no new IPC" because `ProjectPicker` already holds `recents` from `list_projects` (`ProjectPicker.tsx:146`). That is true of the *picker* but **incompatible with hosting the invite at the app shell**: `list_projects` is invoked **only** in `ProjectPicker.tsx`, and `App.tsx` holds no project-list or count state (both verified 2026-07-28). The two decisions were jointly unrealizable as written.

**Resolution:** `App.tsx` does its **own** `list_projects` invoke for the count — a second call site, accepted deliberately. Rationale: (a) it is a cheap read of a ≤100-entry JSON file, already re-invoked on every picker mount, so a second call is not a cost worth designing around; (b) the alternatives are worse — lifting `recents` into a shared store is real refactoring of a working surface for one boolean's benefit, and prop-drilling a count *up* from the picker inverts the ownership (the invite must be able to fire on a scene the picker does not own); (c) it keeps the invite genuinely app-level, which is what verdict (a)'s strip retirement requires. **WP3 must gate this read on `workflow_invite.is_none()`** so the extra IPC is skipped entirely once the invite has resolved — which is permanently, for all but first-run users.

**AppSettings field(s):** one new field —

Follows the established optional-with-default + `rename_all = "kebab-case"` enum shape (`PipMode`, `pip/layout.rs:43-55`; `CcPermissionMode` uses explicit per-variant renames for CLI fidelity, which does not apply here). **Field-count bookkeeping (corrected at verify-self, 2026-07-28):** `AppSettings` currently carries **7** fields (`pip_layout`, `pip_mode`, `cc_permission_mode`, **`cc_yolo`**, `time_tracking_enabled`, `update_notifications_enabled`, `skipped_version`), of which only **5** are user-facing preferences — `cc_yolo` is a dead legacy field (retained purely so a pre-dropdown `settings.json` round-trips; never written, `skip_serializing_if` self-cleans it) and `skipped_version` is updater bookkeeping, not a preference. **Default:** `None` (absent from `settings.json` — so an existing install and a fresh one both read "never shown", which is correct for a brand-new feature).

**Three buttons, three intents (operator-corrected at verify-human, 2026-07-28 — supersedes an earlier two-button `[Enable]`/`[Not now]` draft).** The earlier draft defined `[Not now]` as *permanent* suppression, which is a **mislabeled control**: a button reading "Not now" that means "never again" lies to the user. | Button | Persisted write | Effect |
|---|---|---|
| **`[Install & enable]`** (or `[Enable]` when the substrate is already present) — ⚠️ **SUPERSEDED 2026-07-29: routes to Settings, records `Some(Acknowledged)`, does NOT flip the gate. See "Verdict (b) revision" below.** | `workflow_invite = Some(Enabled)` + gate ON | Features on; never re-shown. |

`[Later]` is the *absence* of a write — pure React state, mirroring the updater's `dismissBanner` (`useUpdater.ts:180-183`, which clears the banner with `setBanner(null)` and persists nothing, so it reappears next launch) exactly as `[Dismiss]` mirrors `skipVersion` (`:173`, which writes `skipped_version` to disk for permanent suppression). **That precedent is the reason `[Later]` needs no new field** — the existing `None` state already means "unresolved," and a session-scoped hide is a React concern, not a persistence one.

**Consequence — the enum variants ARE load-bearing, not diagnostics.** *(This reverses a line in the earlier draft.)* With a real `[Later]`, the three arms differ by *which write happens, or doesn't*: `None` (re-showable) vs `Some(Dismissed)` vs `Some(Enabled)`. **`workflow_invite` is internal state, not a user-facing setting** (operator-confirmed at verify-human). It gets **no control in the Settings panel** — it is written only by the invite's own three buttons and read only by the show-predicate. The Settings panel exposes exactly one new *setting*, `workflow_features_enabled`; the invite's lifecycle is invisible there. So M10.9 adds 2 struct fields but only **1** visible setting.

This is what settles the **disable-after-enable case**, which a naive `workflow_invite_seen: bool` handles only by accident and a "derive it from the gate" approach gets actively wrong: a user who enables the features, tries them, then disables returns to `workflow_features_enabled == false` — the *same* gate state as a user who never saw the invite. With the outcome recorded separately, `workflow_invite == Some(Enabled)` suppresses forever and they are not re-pitched something they already evaluated and rejected. **Once `workflow_invite` is `Some(_)`, suppression is permanent and one-directional — nothing in the product ever resets it** (no "show me that invite again" affordance — out of scope; the Settings panel is the durable route to the gate). `[Later]` is not an exception to this: it never writes, so it never enters the suppressed state in the first place.

**Dev re-drive:** a **`window.__workflowInviteReset()`** frontend seam registered **only** under `import.meta.env.DEV`, mirroring the two existing dev seams exactly — `window.__seedWorkspace` (`App.tsx:498-514`) and `window.__editorSynthetic` (`EditorSplit.tsx:463-476`) — declared as an optional member on `Window` in `src/vite-env.d.ts` so the type reflects its absence in production. **Invite host — the now-fired "Also confirm" clause.** *(⚠️ The "primary button flips the gate inline" sentence in this paragraph is **SUPERSEDED 2026-07-29** — see "Verdict (b) revision" below. Everything else here — app-level host, modal-not-banner — still stands.)* WBS 1.(b) asked to confirm the invite has a home that isn't the picker *if* (a) landed on option (iii). It did (**iii-b**), and that verdict **retires the picker settings strip** — so the invite is **its own app-level component**, not a strip row. - **Backend field** — `AppSettings` (`src-tauri/src/config_store/settings.rs:37-97`) is a flat all-`Option` struct; every field carries `#[serde(default, skip_serializing_if = "Option::is_none")]` so an older/fresh file round-trips forward-stably. `time_tracking_enabled` (`:68-77`) is the closest template: `Option<bool>`, default applied by the **reader** (`read_time_tracking_enabled:199`) not by serde, with a read-modify-write setter (`write_time_tracking_enabled:207`) that preserves the other fields.
- **Frontend seed + sync + optimistic-set + revert** — the picker runs this triple three times over (`ProjectPicker.tsx`: permission mode `:164-202`, time tracking `:209-250`, update notifications `:253-330`). The shape: on mount, `invoke` the getter and `setState` (guarded by a `cancelled` flag for StrictMode), `listen()` to the broadcast event so *any* mirror surface flipping the value re-syncs this control, then on user change do an **optimistic** `setState` → `invoke` the setter → **revert to the prior value + error toast** via `mapIpcError` on rejection.
- **Menu mirror** — handles to the `CheckMenuItem`s are stashed in Tauri managed state at build time (`app_menu/mod.rs:87-91` `PipModeMenuItems`, `:122-124` `CcPermissionModeMenuItems`) because **there is no menu-rebuild path**; a broadcast listener wired in `lib.rs` calls `apply_pip_mode_to_menu` / `apply_cc_permission_mode_to_menu` (`:99`, `:131`) to re-check them. A boolean gate needs one `CheckMenuItem` and the same stash+apply pair.
- **Id byte-identity** — the menu item's id string must be added to Rust `ids` + `FUNCTIONAL_IDS` (`app_menu/mod.rs:186-208`) **and** to TS `MENU_IDS` (`src/menu/menuBridge.ts:26-56`) byte-for-byte; an existing test greps that every `FUNCTIONAL_IDS` entry appears as a quoted `MENU_IDS` value (`:516-537`). `menuActionFor` then maps the id to either a synthetic `keydown` or a named React callback seam (`menuBridge.ts:72-98`) — a gate toggle is a **callback**, not a key (it has no chord, and per the WBS's OFF-invariant no workflow chord may exist while OFF).
