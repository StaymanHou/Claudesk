# Vision — Claudesk

## Vision

**The problem.** Starting work on any given project takes minutes of repetitive setup: open a terminal, `cd` to the project, launch `claude`; open Sublime Text and load the project; open Sublime Merge and load the project again; sometimes open a second terminal and `cd` again. The cost is small in isolation but ruinous in aggregate — 20+ active projects rotate through the queue, 3–4 are in flight on any given day, and each context switch pays the setup tax again. The setup friction discourages quick-pop-in visits to older projects and breaks flow when juggling several at once. Compounding it: when several projects ARE in flight, finding the one waiting on input means clicking through windows or switching Spaces — a second-order tax on top of the launch tax.

**The solution.** Claudesk — a macOS-only, single-user, open-source "lite IDE" that puts everything in **one window with multiple virtual workspaces inside it**:

- **VSCode-style project picker** — pick from a list of known projects, click, and the full environment fires up in <10s. Picking a project opens it as a **workspace** inside the existing Claudesk window (a new tab/stage), not a new OS window.
- **One workspace = one project = one CC session.** A workspace contains: Claude Code (PTY-backed terminal) on the left, lite editor + git diff viewer on the right (Phase 3; placeholder in Phase 1), and the workspace's own header chrome (skill buttons, a `/session-start` button). Single-window holds N workspaces concurrently. *(⚠️ Revised 2026-08-11, M12 WP4d: the **drive-mode selector is NOT here** — it lives on the **picker row**. See the drive-mode bullet below.)*
- **Mission Control-inspired layout.**
    - **Center stage:** the currently-focused workspace, full-size, fully interactive (CC terminal, editor, etc.).
    - **Top filmstrip:** live thumbnails of every open workspace, in a **user-arranged order** (drag-and-drop to reorder; the order persists). Each thumbnail shows the project name, an idle/running CC indicator, and a miniaturized rendering of the workspace contents. **The currently center-staged workspace keeps its tile in the filmstrip too** — rendered as a static, active-marked placeholder (project name + status dot, no live mirror, since it's already full-size on the center stage) so the filmstrip is a complete roster and tile positions never renumber when the focus changes. **Clicking a thumbnail promotes that workspace to center stage** and demotes the previous one. A `⌘⇧+digit` hotkey jumps straight to the Nth filmstrip tile (the keyboard equivalent of clicking it). The filmstrip can be **collapsed to a row of mini status tiles** (project name + idle/running dot, no live preview) to reclaim vertical space — toggle via window chrome.
    - The cross-window status indicator from the previous vision iteration is **replaced**: idle-vs-running of every workspace is now intrinsic to the filmstrip/tile row, always in view inside the Claudesk window itself.
- **Picture-in-picture mini player (tri-state mode, display-only).** A small always-on-top secondary window that surfaces the same idle/running status for every open workspace when the Claudesk window loses focus (different macOS Space, another app focused, Claudesk minimized) — so the "which project is awaiting input" question is answerable without bringing Claudesk forward. Its visibility is an explicit **tri-state mode — Off / On (pinned) / Auto (default)** — directly selectable from the right-panel PiP icon (cycles Off→On→Auto) and a View-menu radio. **Auto** (the default) is hidden while Claudesk is focused, **summons itself** on a sustained (~3s) main-window blur, and dismisses on refocus; **On** keeps it shown + pinned across focus changes; **Off** keeps it hidden. *(Revised 2026-06-27, M5 WP5: this REVERSES the earlier "Toggled on/off explicitly by the user; not auto-summoned" stance — auto-summon is now adopted, as the default Auto mode. The tri-state replaced an earlier bool auto-summon-setting + manual-toggle model that had a dead-end. See the revision note at the top.)* Display-only in v1 — clicking a tile does NOT bring the workspace forward; the user switches back to the Claudesk window normally (⌘Tab, Mission Control, Dock). The mode changes *when the panel appears*, not what a tile click does.

  > **OPEN DESIGN QUESTION** (defer to `/product-research`): Even a user-toggled, display-only PiP doesn't fully solve "Claudesk is hidden and PiP is off." A small **menu-bar item** (always visible system-wide, native macOS surface, cheap to build) would. The trade-off is one more surface to maintain and a duplication of what the filmstrip/PiP already show. Research should determine: (a) is the menu-bar item warranted as a parallel always-on surface; (b) if yes, should PiP become click-to-focus (richer but more complex) and the menu-bar item stay display-only-with-click-to-bring-app-forward, or some other split.

- **Left half of each workspace: Claude Code**, in yolo mode by default, already `cd`'d into the project.
- **Right half of each workspace: a built-in lite editor + git diff viewer** covering the daily-use Sublime Text features (multi-cursor / column selection, Cmd+P fuzzy file finder, command palette for syntax selection, project-wide find/replace, split panes, minimap). The in-app editor is meant to **replace** Sublime Text for routine work, not coexist with it: a hotkey switches the right half between editor ↔ diff viewer (↔ second terminal). The Phase-1 "pop the real Sublime Text" hotkey is a **stopgap** that exists only until the in-app editor lands, then is removed. *(**Sublime Merge is the exception — it stays as a permanent companion surface.** The in-app diff viewer covers inline *viewing* of the working diff, but staging, blame, history, and inspecting a file's content at a past commit stay in Sublime Merge; an "Open in Sublime Merge" launch button is a permanent right-half affordance. Revised 2026-06-20 — the prior wording said the diff viewer fully covered Sublime Merge.)*
- **Stateful CC controller, not just an embedded terminal.** Claudesk owns each workspace's CC process lifecycle, watches workflow state files (`workflow/.session.md`), and exposes workflow operations as clickable buttons.
- **A thin orchestration layer above CC.** Clickable buttons for every custom workflow skill — no typing slash commands. A single "Recycle Session" button performs the manual ritual (`/session-handoff` → wait for completion → Ctrl+D → spawn fresh CC → `/session-restore`) in one click. Triggered on user judgment, never automatically.
- **Smart auto-resume on workspace open (M12 — ✅ SHIPPED 2026-08-05).** When a workspace opens (project picked from the picker), Claudesk fires the right resumption command by itself — and **announces it before you click**. **TWO** signals, not three:

  | # | State signal | Meaning | Fire |
  |---|---|---|---|
  | 1 | **Unclean-exit flag** set | Mid-step termination (crash, power-off, force quit) — CC remembers, the workflow doesn't | **`--continue` CLI flag** at spawn |
  | 2 | `workflow-system/state/.session.md` exists | Handed off via `/session-handoff` — explicit next-step recorded | `/session-restore` (PTY inject) |
  | — | Neither | Fresh start | ***nothing fires*** — `/session-start` is never auto-fired; it gets an explicit button |

  ⚠️ **"Two signals" means two things that FIRE.** The third row is deliberately unnumbered: it is the **absence** of both signals, not a third detector. The original spec's third *branch* is what made this feature undeliverable (see below), so the count is load-bearing rather than stylistic.

  ⚠️ **Precedence: signal 1 BEATS signal 2** — an explicit user signal outranks a semi-automated file. (This is the **reverse** of the original spec, and is mutation-proven in `predictAction.ts`.) The two arms differ in **kind** — argv at spawn vs. a PTY inject ~1500 ms later — which is why the predictor returns a tagged union rather than a string. Auto-fire is **announced** on the picker row, and a second door (`⊘`) opens the workspace **without** firing; with no prediction the two doors are identical, so the second is absent. This is a **per-open routing decision, not a per-project preference** — nothing is persisted by either choice.

  ⚠️ **THE ORIGINAL THREE-BRANCH SPEC WAS DISPROVEN AT DECOMPOSITION (2026-08-03) AND MUST NOT BE REINSTATED.** It is recorded here rather than deleted so nobody re-derives it. Its middle branch keyed on *"does CC have a resumable conversation for this dir?"*, which is **unqueryable** — `claude --help` exposes `-c/--continue` and `-r/--resume` to **act**, but nothing to **ask** — and **permanently true**, because the transcript store never prunes (194 transcripts for this project, 313 older than 30 days; a throwaway scratch dir had 5). As specced, that arm fires for any directory ever opened, **starving `/session-start` forever**, and would resume a 40-day-old unrelated conversation because a file exists. The fix **deleted the unknown instead of solving it** (design prior `prefer-an-explicit-user-signal-over-an-unobservable-inference`): the unclean flag is **default-set on workspace open** and cleared **only** by a clean exit, so a power loss — which runs no code — and a button click produce **identical state**, and the design fails toward "resume the mid-flight workflow." Firing consumes the flag. ⚠️ Note also that `/session-pause` and `/session-resume`, named in the original table, **have not existed since M9 WP5**.

- **Drive-mode selector + indicator on the PICKER ROW.** The four drive modes (1 `stepping` / 2 `orchestrated` / 3 `autopilot` / 4 `fsd`) govern how aggressively the workflow orchestrator chains between skills. Today they're selected via prompt text with no visible reminder of the active mode. Each project row in the picker carries the mode next to the model override — current mode always visible, click to change — so the mode is chosen **where the spawn is chosen**. Persisted per-project in Claudesk's own `projects.json`, and delivered to the CC session as an **env-var-gated `UserPromptSubmit` hook signal**, so a Claudesk-opened session is not re-asked a question the operator already answered.

    ⚠️ **Three corrections recorded here 2026-08-11 (M12 WP4d), because the original text of this bullet was wrong in ways a future reader would otherwise re-derive:**
    - **NOT the workspace header** (operator decision 2026-08-03, consistent with where M11.5 WP1's model control landed after being rejected on the header). This is the **first live edge case** for design prior `set-a-spawn-time-choice-where-the-spawn-is-chosen`, whose own text names itself untested: drive mode is read at spawn **and** is live-reconfigurable, so it could defensibly live in both places. Resolved **picker row only, not both** — two homes for one per-project value would need a sync path that deliberately does not exist.
    - **The mode is NOT mirrored into the active WIP file's `drive_mode:` frontmatter.** That mechanism (the original wording here: *"single source of truth"*) was **REJECTED** at the WP4 re-decomposition. `/session-restore` **deletes** `.session.md` at its step 7 and `feature-finalize` **archives** the WIP file, so at the exact moment a new work package starts **there is no file to write to** — and five WIP templates never declare the field. Measured, not assumed: a persisted mode already exists in **93%** of manual restores and is **already ignored 74%** of the time, so one more copy on disk changes nothing. **Claudesk reads the workflow's world; it does not write it.**
    - **The wire vocabulary was wrong on 2 of 4 values** — this bullet said `step-by-step` and `full-autopilot`, which **no workflow skill recognizes**. The authoritative values are `stepping` and `fsd` (upstream `transitions.md`; pinned in Claudesk by per-variant serde renames in `config_store`).

Built with Tauri (Rust backend, web frontend) to stay genuinely lightweight. The single-window-with-many-workspaces model is also a friendlier fit for Tauri than N independent windows — one WKWebView, one Rust process, one PTY-host owning N child PTYs.

## Target Audience

**Single user: the author (Stayman).** This is a personal tool, designed against one person's exact workflow — heavy Claude Code use, the custom workflow-system skill set installed at `~/.claude/skills/`, daily use of Sublime Text, macOS-only, 20+ rotating projects. Open-sourced so anyone running a similar setup can use or adapt it.

**Two tiers, one app (stance refined 2026-07-20).** The earlier framing was "no design concession is made for users who don't share the workflow." That's refined — *not reversed* — because the old wording implied a secondary (non-workflow) user would hit dead affordances (an empty Docs tab, controls pointing at absent files), which is bad for them and clutter for the primary user. The refined stance:

- **The workflow-independent lite-IDE core** (project picker, tabbed workspaces, PTY terminals, editor/diff/second-terminal, and the hook-driven status surfaces — filmstrip / PiP / menu-bar, all built on Claude Code's *native* hook channel) is for **any** Claude Code user, out of the box, zero config. This is the bulk of the product and it is *optimal for both* audiences with no compromise.
- **The workflow-orchestration layer** (Docs viewer, smart auto-resume, drive-mode selector, skill-buttons — everything that assumes the custom workflow system) is **opt-in and gated** behind a single `workflow_features_enabled` setting (default OFF; Milestone 10.9). With the gate OFF the app is **byte-identical** to one that never had those features — no dead affordances. A one-time evangelistic invite offers to enable + explains how to install the companion workflow system.

**What "no concession" still means (unchanged):** no feature is *built for* the secondary user at the primary user's expense, and the roadmap is not distorted for them. The refinement only forbids *dead affordances* — it does not add features for, or compromise the tool toward, non-workflow users. The primary user (operator) enables the gate once and gets the full, undiluted workflow-aware tool. The companion workflow system itself (install/uninstall, doc layout, onboarding) is owned by the separate `my-claude-code-customization` repo. *(Full gate design: `roadmap.md` → Milestone 10.9 + Revision 2026-07-20. Design lean: `design-priors.md` → the workflow-feature-gating prior.)*

## Success Metrics

1. **Time-to-productive on a project drops from ~minutes to <10s.** Click a project in the picker → a new workspace opens in the current Claudesk window with CC running in the project dir, editor loaded, ready to type.
2. **The clean-context ritual becomes one click instead of a 4-step manual dance.** ✅ **MET — M13 WP3, verified end-to-end on a real session 2026-08-18 (WP4 Phase 3).** "Recycle Session" replaces the manual dance in one click.

    ⚠️ **Two corrections to this metric's own wording, 2026-08-18 (M13 WP4).** The steps it names are **not** what shipped and two of them never existed. **`/session-pause` and `/session-resume` DO NOT EXIST** — renamed `/session-handoff` / `/session-restore` at M9 WP5 (the same correction metric 5 carries). And the teardown is **NOT Ctrl+D**: Recycle reuses the pane's existing `handleRelaunch`, so exactly one respawn route exists. **As built:** `/session-handoff` → wait for a **composite** completion marker → clear the unclean-exit flag → kill + respawn → `/session-restore` into the fresh session. ⚠️ The wait is **not** "the `.session.md` write" — WP1 measured the pointer landing well *before* the skill finishes, so firing there kills CC mid-skill; the marker is a fresh write **followed by the next `Stop`**. ⚠️ **Recycle is also a callable operation, not only a button** — M15's context-pressure rule is the planned non-click caller.
3. **Never have to type a slash command again for common skills.** ✅ **MET — M13 WP2, verified live 2026-08-18 (WP4 Phase 2).** The skills the operator actually fires are one click, in the workspace header.

    ⚠️ **"Every installed workflow skill" was REFUTED by measurement and is not what shipped, deliberately (M13 WP1, operator sign-off).** Across 2470 transcripts, only **11 of 50 invocable skills were EVER typed by hand**, and **zero** `feature-*` / `task-*` / `product-*` invocations ever — those are the *agent's* vocabulary, fired by auto-chaining. Rendering all of them would have surfaced the agent's working set to a human who never reaches for it, and a 61-button wall (11 of those entries being dead symlinks) is a worse launcher than typing `/fea`+tab. ⚠️ **The metric's operative word is the exit criterion's: "common" skills, not "all".** As built: a **fixed set of five** — `/session-start`, `/session-restore`, `/session-capture`, `/util-prune-claude-md`, `/util-backlog-paydown` — plus Recycle as a sibling affordance (an *operation*, not a slash command). Three of the five are low-frequency and were included **knowingly**, so the metric is carried by a visible surface rather than closed by argument.
4. **Finding the awaiting-input CC across multiple workspaces takes <1 second of visual scan, zero clicks, from inside the Claudesk window.** The filmstrip (or its collapsed mini-tile row) shows idle/running for every workspace at all times. Switching to that workspace is one click.
5. **Returning to a project is one click, regardless of how the prior session ended.** Whether the last session was handed off with `/session-handoff`, killed mid-step by a power-off, or cleanly closed at finalize, picking the project drops the user into the exact right resumption state without choosing between `/session-restore`, `--continue`, and `/session-start` manually. The active drive mode is visible **on the picker row**, at the moment of the click that uses it — no prompt-level ritual to recall it.

    ⚠️ **Three corrections, 2026-08-11 (M12 WP4d) — this metric was UNSATISFIABLE as written:** it required the mode to be *"always visible in the workspace header"*, which is not where it shipped, so the metric could never be met by the real app. It now reads against the picker row. **`/session-pause` and `/session-resume` DO NOT EXIST** — renamed `/session-handoff` / `/session-restore` at M9 WP5, specifically to stop `/session-resume` colliding with the built-in `/resume` that this very metric depends on. And the resumption vocabulary is now the **as-built two** (M12 WP1–WP3): an unclean-exit flag → the **`--continue` CLI flag** (⚠️ not a typed `/resume`, which opens an interactive picker), else `.session.md` present → `/session-restore`, else **nothing auto-fires** — `/session-start` is never auto-fired and gets an explicit button. ⚠️ **The unclean flag BEATS `.session.md`** (an explicit user signal outranks a semi-automated file).
6. **Finding the awaiting-input CC when the Claudesk window is NOT in focus** (different macOS Space, another app foreground, Claudesk minimized) **takes <1 second of visual scan via the PiP mini player or its equivalent, zero clicks to assess.** The PiP's **Auto** mode (M5 WP5, default) serves this directly — it summons itself on a sustained blur, so the glance surface appears exactly when Claudesk is out of view without the user remembering to summon it first. Acceptance for this metric depends on the open menu-bar-item question — the research pass decides whether PiP alone meets it or a menu-bar item is also required.

## Core Principles

1. **Lite over featureful.** If it's not a daily friction, don't build it. Reject scope that turns this into a general-purpose IDE.
2. **CC-process-aware AND workflow-state-aware, not just terminal-embedding.** Claudesk understands each workspace's CC lifecycle (idle vs running) via Claude Code's official hook channel — `UserPromptSubmit` / `Stop` / `Notification` / `PostToolUse` events written to `~/.claude/settings.json` — and reads workflow state via known files (`workflow-system/state/.session.md`, `.claude/skills/`). It uses those signals to make the right decision on workspace open (the `--continue` flag, `/session-restore`, or nothing), to keep its UI honest, and to populate the filmstrip / PiP / menu-bar status surfaces. It NEVER infers state by scraping the terminal's text output. This is the architectural line that separates this tool from "tmux with a nicer skin."

    ⚠️ **Corrected 2026-08-11 (M12 WP4d).** The original text said the drive-mode indicator *"reflects the WIP file's `drive_mode:` frontmatter, not a separate in-memory toggle"* — **that is backwards from what shipped.** The indicator reflects Claudesk's **own** per-project `projects.json`, and the mode reaches CC as an env-var-gated hook signal. **Claudesk never writes into `workflow-system/`** (M11 shipped the docs viewer read-only and M12 did not change that); the WIP frontmatter remains the *workflow's* own source of truth, written by the skills. The principle still holds — state comes from files and hooks, never from scraped output — but the direction of that particular arrow was wrong.
3. **The Sublime *features* are sacred — and both Sublime apps stay as permanent one-click companions.** The built-in editor must preserve the daily-use Sublime feature set (multi-cursor, Cmd+P, command palette for syntax, project find/replace, split panes, minimap) so that in-app editing is a genuine replacement, not a second-class compromise. The right half is the **primary** editing home; a hotkey switches it between editor ↔ diff viewer (↔ second terminal). **Both Sublime apps remain permanent escape hatches, launched on demand from icon buttons in the right-panel tab row:** Sublime **Text** for when the operator wants the full real editor, and Sublime **Merge** for richer git work — staging, blame, history, inspecting a file at a past revision — that the inline diff viewer (inline *viewing* only) doesn't do. *(Revised 2026-06-20, WP8: Sublime **Text** is KEPT permanently, reversing the 2026-06-19 "external Text pop removed once the editor lands" framing — the in-app editor is primary, but a one-click Text escape hatch costs nothing and the operator wanted it retained. WP8 only deleted the redundant `⌘⇧O` Text hotkey, not the button. Sublime **Merge** was already permanent per the 2026-06-20 WP5 revision.)*
4. **One window, many workspaces, fewer prompt-level rituals.** The user should never manage OS windows for Claudesk itself — multiple projects live as workspaces inside the single Claudesk window, switched via filmstrip thumbnails. Right-half swapping within a workspace (editor / diff viewer / second terminal) happens inside that workspace. Persistent controls live on the picker row (drive-mode selector, model override), in the workspace header (skill buttons), or in window chrome (filmstrip collapse toggle, PiP toggle). *(⚠️ Corrected 2026-08-11, M12 WP4d — this read "workspace header (drive-mode selector)".)* A state that affects how every skill runs should be visible at a glance and changeable with one click, not buried in prompt text the user has to remember to type.
5. **No script-per-project, no per-project config burden.** Adding or removing a project from the picker is trivial — no `.claudesk.json` per repo, no bespoke launcher per project.
6. **Status visibility scales beyond the foreground.** Whatever workspace the user is focused on, and whatever app or Space they're switched into, the idle/running state of every CC session should be reachable at-a-glance with at most one action (open the PiP, glance at the menu-bar). The cost of forgetting a project is going-cold context — the status surfaces exist to prevent that, and they must work both inside Claudesk and outside it.

## Anti-Goals

- Not a VSCode replacement or general-purpose IDE.
- Not cross-platform — macOS only.
- Not multi-user; no team or sharing features.
- Not a Claude Code fork — Claudesk wraps the official CLI.
- Not an extension ecosystem.
- **Not multi-window for Claudesk itself.** Multiple projects = multiple workspaces inside one window. (The PiP mini player and the menu-bar popover are the auxiliary surfaces; Claudesk itself stays single-window. The Sublime Text / Sublime Merge windows are *external apps* launched on demand — kept permanently per Core Principle 3 — not Claudesk windows, so they don't bear on the single-window rule.)
- **Not PiP click-to-focus in v1.** Display-only. Click-to-focus is a Future Possibility if the display-only surface proves insufficient in dogfooding.

## Future Possibilities (Not in Initial Roadmap)

Noted here so the architecture leaves room for them; explicitly NOT scoped into the initial roadmap.

- **PiP click-to-focus.** Promote a workspace from a PiP tile click — bring the Claudesk window forward and switch center stage to that workspace in one action. Defer until display-only PiP has been used long enough to confirm the limitation is real.
- **Migrate workflow state-machine enforcement into Claudesk.** Today the state machine documented in `_ref/claude-customization/docs/product/transitions.md` (product / feature / task / incident workflows; SURFACE / ESCALATE / REDIRECT cross-level mechanisms; AUTO/PAUSE drive modes; back-loop guards) is enforced advisorily — purely through `~/.claude/CLAUDE.md`, the per-workflow `AGENTS.md` orchestrator files, and individual skill prompts. Tuned to acceptable consistency but not perfect. Claudesk, as a stateful CC controller that already watches `workflow/.session.md` and can read `.claude/skills/`, is well-positioned to host harder enforcement (e.g., warn or block on out-of-state skill invocations) and to render a GUI visualization of the current workflow state, valid next transitions, drive mode, pending SURFACE/ESCALATE items, and back-loop history. Build Claudesk so this is a natural future addition — don't paint into a corner that assumes CC is a black box.
- **Time tracking integration.** The existing `claude-time` hook system at `_ref/claude-customization/tools/claude-time/` logs Claude Code hook events to a local SQLite DB and produces per-project / per-session / per-day time reports (tool time, active time, reading/thinking/away buckets, cross-session typing-debit attribution). Claudesk can plug into this in two ways down the line: (1) **richer signals** — Claudesk-level events (workspace switched, panel swapped, Sublime popped, Recycle Session clicked, skill button clicked) feed the same SQLite DB to give a more precise picture than hook events alone; (2) **in-window visibility** — surface `claude-time report` output (today's totals, per-project breakdown) inside the Claudesk UI rather than requiring a separate terminal invocation. Particularly valuable for the multi-workspace use case where "where did this week actually go" is a real question. **Note:** the in-roadmap filmstrip + PiP status surfaces tap the same hook channel (`UserPromptSubmit` / `Stop` / `Notification`) that `claude-time` uses, so Claudesk will already be registering a hook handler in `~/.claude/settings.json` by the time this future integration matters — sharing or co-locating with `claude-time` should be straightforward.
